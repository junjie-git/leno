## 1. 修复执行摘要（Outbox 发布器）

### 1.1 缺陷重述
域事件经 `SaveChangesWithOutboxAsync` 与业务数据同事务写入 `outbox_messages`（写路径完整），
但**没有任何 BC 注册 Outbox 后台发布器**（读路径缺失），消息将永久停留在 `Pending`，
所有跨 BC 异步链路静默失效。

### 1.2 修复过程中暴露的第二层缺陷
`ShardedOutboxPublisher<TDbContext>` 以 `AddHostedService`（singleton）注册，
却在构造函数注入 `IEventBus`（`services.AddScoped<IEventBus, RabbitMqEventBus>()`）。
这是 **captive dependency（捕获依赖）**：在 `ValidateScopes` 开启时（Development 环境默认开启）
会导致宿主启动直接失败。因此"补一行注册"的朴素修复会立刻让本地开发环境崩溃 ——
修复必须同时打断该依赖。

### 1.3 实际改动

| # | 文件 | 改动 |
|---|------|------|
| 1 | `src/BuildingBlocks/Leno.Infrastructure.Persistence/Outbox/ShardedOutboxPublisher.cs` | 构造函数移除 `IEventBus` 参数；改为在每条消息的独立作用域内解析 `IEventBus`（`PublishSingleByIdAsync` 中与 `TDbContext` 同作用域），`PublishSingleAsync` 相应新增 `eventBus` 形参。补充 XML 文档说明为何不得构造注入。 |
| 2 | `src/BuildingBlocks/Leno.Infrastructure/Dependencies/WebApplicationExtensions.cs` | 在 `AddLenoApi<TDbContext>` 组合根统一调用 `services.AddShardedOutboxPublisher<TDbContext>(configuration)`，一处覆盖全部 19 个 BC；新增 `using Leno.Infrastructure.Outbox;`，同步更新方法 XML 摘要。 |
| 3 | `src/BuildingBlocks/Leno.Infrastructure.Tests/Outbox/ShardedOutboxPublisherTests.cs` | `LinqBackedShardedOutboxPublisher` 子类与 `CreateSut` 同步去掉 `eventBus` 形参；改为在 `ServiceCollection` 注册 `IEventBus` mock（更贴近真实解析路径）；2 处配置校验测试同步调整。 |

### 1.4 验证结果

- `dotnet build Leno.slnx` → **Build succeeded，0 Error**（763 Warning 全部为既有 `LENO_PM_BC_SPLIT` 等历史告警，与本次改动无关）
- `dotnet test --filter "FullyQualifiedName~Outbox"` → **63/63 Passed**
- 未引入新告警；受影响程序集 `Leno.Infrastructure.Persistence` / `Leno.Infrastructure` / `Leno.Infrastructure.Tests` 均 0 warning

### 1.5 部署待办（修复后仍需运维侧动作）
- 单实例：无需配置，默认 `ShardCount=1 / ShardId=0`
- 多实例：需为每个实例注入 `OUTBOX__SHARDING__SHARD_ID` 与 `OUTBOX__SHARDING__SHARD_COUNT`（或写入 Consul KV `leno/config/Outbox__Sharding__*`）

#### B4 — 延迟消息调度器"已使用但未配置"（**2026-09-21 升级为 P0**）
- **位置**
  - 调用方：`Order/…/Services/OrderAppService.cs:318`（`ConfirmReceiptAsync` → 调度 `queue:order-after-sales-window`，7 天后关闭售后窗口）
  - 调用方：`Order/…/Services/OrderSagaOrchestrator.cs:144`（调度 `queue:order-timeout`，30 分钟超时取消）
  - 消费方：`OrderTimeoutDelayMessageConsumer`、`AfterSalesWindowConsumer`
- **复核结论（静态）**
  - 全仓检索 `UseDelayedMessageScheduler` / `AddDelayedMessageScheduler` → **零调用**；
    `AddEventBus`（`Leno.Infrastructure/Dependencies/ServiceCollectionExtensions.cs:140-198`）只配置了
    `UseMessageRetry` 与 `ConfigureEndpoints`，没有任何 scheduler 注册
  - `docker-compose.yml:52` 的 broker 为 `rabbitmq:3.12-management`，
    **未挂载 `enabled_plugins`、未启用 `rabbitmq_delayed_message_exchange`**
  - 两处 `CreateMessageScheduler()` 调用**均无 try/catch**

- **影响**：MassTransit 的 RabbitMQ 延迟调度必须显式启用（插件或 Quartz），

  以 `ConfirmReceiptAsync` 为例，`SaveEntitiesAsync` 已先提交订单状态与 `AfterSalesWindowEndsAt`，
  调度失败会**留下"已确认收货但售后窗口永不关闭"的半成品状态**，同时向调用方返回错误
- **是否需处理**：**是（P0，需运行时验证）** —— 属"功能正确性"而非"技术债"。
  建议：起 staging 调一次确认收货，观察是否抛 `ConfigurationException`/`InvalidOperationException`，
  或直接查 `order-after-sales-window` 队列是否存在延迟消息。修复方向二选一：
  (a) 启用 broker 插件 + `rabbitCfg.UseDelayedMessageScheduler()`；或
  (b) 改用持久化调度（如 Quartz + 传输无关调度器），避免依赖 broker 插件
- **连带影响**：**D1（Saga）与 D2（Process Manager）的切流演练必须先解决本项**，
  否则 `flag=true` 会在下单/收货路径上直接报错

### H. 数据库迁移双路径（2026-09-21 新增）

#### H1 — Helm 迁移 Job vs 应用启动时 EF 迁移（同一 `__EFMigrationsHistory` 双写）
- **位置**

    SQL 副本位于 `deploy/helm/leno/files/migrations/`）；由 `values.yaml:280-283` 的 `migrations.enabled=true` 全局开关控制
  - 路径 B（运行期）：各 BC `Program.cs`（如 `Leno.Order.Api/Program.cs:52`）
    —— `await app.Services.MigrateWithLockAsync<XxxDbContext>()`，直接应用 EF Core 迁移，带 Redis 分布式锁
  - 两者写入同一张 `__EFMigrationsHistory` 表
- **原因**：`migration-job.yaml` 顶部注释说明 —— 原用 `dotnet ef database update` 的运行时镜像不含 SDK 必然失败，
  改为预生成幂等 SQL + sqlcmd；但应用启动时的 `MigrateWithLockAsync` 并未同步移除
- **影响**
  - 同一数据库被迁移两次（先 Job、后每个副本启动时）；虽然幂等 SQL 带 `IF NOT EXISTS` / `__EFMigrationsHistory` 守卫，
    但**两条路径的事实来源不同**：一次是手写生成的 SQL，一次是 EF 模型。
    若 `files/migrations/*.sql` 与 EF 快照漂移，Job 先执行的 SQL 会让 EF 认为迁移已应用（历史表命中），
    从而**静默跳过**模型中已存在但 SQL 未覆盖的变更
  - 副作用：每个副本启动都尝试迁移（Redis 锁串行化），启动链路耦合数据库
- **✅ 2026-09-21 深化取证（重要）**：迁移机制实际分成**三类**，比原判断更broken
  1. **已在 EF 管线内（11 个 BC）**：`generate-migration-scripts.ps1` 用 `dotnet ef migrations script --idempotent`
     从 EF 迁移生成 SQL —— 这部分是干净的
  2. **手写 SQL 冒充生成物（identity + accesscontrol）**：`identity-accesscontrol-initial.sql` 是**手工文件**，
     却被放进生成产物目录（`scripts/migrations/` 与 helm `files/migrations/`），外观与生成物无法区分；
     且 `$bcProjects` 清单里**根本没有这三个 BC**，所以重跑脚本也不会覆盖它
  3. **完全无建表路径（usercenter）**：无 `Migrations/` 目录、无 `usercenter-*.sql`（见 A6/G1）
  - **phantom MigrationId 风险**：`identity-accesscontrol-initial.sql:32` 手工往 `__EFMigrationsHistory`
    插入了一个 **EF 代码库中不存在的迁移 ID** `20260723000000_IdentityAccessControlInitial`；

    `20260723193852_AddPasswordHashVersionColumn`（**均缺 InitialCreate**）
    → 手工 SQL 建表后，EF 会把两个增量迁移当作"待应用"再跑一遍，
    即**运行时正确性依赖"手工 SQL 产物恰好等于 InitialCreate 产物"这一脆弱假设**
- **✅ 决策（2026-09-21）**：采用 **EF 迁移统一**作为事实来源
- **✅ 执行结果（2026-09-21）**
  - 新增 `UserCenter` `20260921060658_InitialCreate`、`AccessControl` `20260921060704_InitialCreate`
  - 删除冲突的手写 `identity-accesscontrol-initial.sql`（两个目录各一份）
  - `generate-migration-scripts.ps1` 的 `$bcProjects` 由 11 → 14（补入三个 BC）
  - 重新生成 `identity-initial.sql` / `accesscontrol-initial.sql` / `usercenter-initial.sql` 并同步到 helm
  - 顺带修复：迁移代码的 **CA1861** 误报 —— 根 `.editorconfig` 新增 `[**/Migrations/**/*.cs]`

## 7. 下一步执行计划（2026-09-21 制定）

### 排序原则

不是按缺陷"严重程度"排，而是按**「是否依赖他人决策」与「是否需要运行时验证」** 排：

1. 先办**不需要任何人拍板、且能立刻做**的事（缺陷与死代码）—— 零协调成本
2. 再办**声明的期限已过、属于计划内收尾**的事 —— 只需确认，不需决策
3. 然后办**需要运行时验证**的事 —— 成本最高、风险最大，必须留出演练窗口
4. 最后办**需要产品/架构决策**的事 —— 依赖信息输入，不能自行推进

### R 组 — RS256 推进新增决策点（2026-09-21，因 Q2 决策派生）

> 完整影响面与阶段划分见 `docs/rs256-推进方案.md`

**R1（最关键）签发权归谁？** —— 三条互斥路线
- **路线 A（推荐）**：先部署 Identity，签发权归 Identity → 需解除 A3 中 Identity 的部署阻塞；符合目标架构、不制造新双轨
- **路线 B**：改造 UserAuth 的 `JwtTokenGenerator` 支持 RSA → 最快见效，但**会新增一条双轨**（两套签名实现），与"消除双轨"方向相反
- **路线 C**：暂缓 RS256，先把 Identity 部署阻塞解决
- 为什么问：**生产实际签发方是 UserAuth（HS256-only），而具备 RS256 能力的 Identity 未部署** ——
  这个错位决定了整条路线的形状，且 A/B 的返工成本差异很大
