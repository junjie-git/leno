## 2. 核心矛盾：签发方归属未定

> **Identity BC 具备完整 RS256 能力，但它没有容器；真正签发 token 的是 UserAuth，而 UserAuth 用的是 HS256-only 的共享内核生成器。**

因此"推进 RS256"绕不开一个前置决策：**签发权归谁**。三条互斥路线：

### 路线 A —— 先部署 Identity，签发权归 Identity（推荐）
- **动作**：解除 A3 中 Identity 的部署阻塞（compose + Helm + 迁移脚本 + 密钥）→ Identity 接管签发 → `SigningMode=Rs256`
- **优点**：符合目标架构（Identity 作为唯一签发方）；**不制造新双轨**；Identity 侧代码已就绪，改动集中在部署
- **缺点**：周期长，依赖 A3（8 个未部署 BC 的整体排期）
- **风险**：签发方切换本身是高风险动作，需与「双签发过渡」配合

### 路线 B —— 让 UserAuth 的 `JwtTokenGenerator` 支持 RSA
- **动作**：扩展 `JwtTokenGenerator` 支持 RS256/Dual（可复用 `RsaJwtSigningService`）→ 验签侧同步改造
- **优点**：不改部署拓扑，最快见效
- **缺点**：**会新增一条双轨** —— 同时存在 `JwtTokenGenerator`（RSA 版）与 `RsaJwtSigningService` 两套签名实现，
  与"消除双轨"的目标方向相反；后续 Identity 上线时还要再收一次
- **适用**：若 Identity 上线遥遥无期，可作为过渡

### 路线 C —— 暂缓，先解 Identity 部署阻塞
- **动作**：把 RS256 与 A3 绑成一个工作流，先推 Identity 部署
- **优点**：不做返工
- **缺点**：RS256 短期不落地

**▶ ✅ 已决策（2026-09-21）：采用路线 A** —— 先部署 Identity，签发权归 Identity。
理由：符合目标架构、不制造新双轨。代价是需先解除 Identity 的部署阻塞。

### 2.1 路线 A 的前置阻塞：UserAuth / Identity / UserCenter 三方重叠（2026-09-21 新发现）

深挖路线 A 的落地条件时发现，**"部署 Identity" 不是加一个服务，而是一次职责迁移**：

三个 BC 存在**逐字相同的路由**（详见 `双轨情况检测报告.md` A6）：

| 路由 | UserAuth | Identity | UserCenter |
|------|:--------:|:--------:|:----------:|
| `api/auth` | ✅ | ✅ | — |
| `api/account` | ✅ | ✅ | — |
| `api/users/me` | ✅ | ✅ | — |
| `api/admin/users` | ✅ | ✅ | — |
| `api/admin/oauth-clients` | ✅ | ✅ | — |
| `api/users/me/addresses` | ✅ | — | ✅ |
| `api/users/me/favorites` | ✅ | — | ✅ |
| `api/users/me/browse-history` | ✅ | — | ✅ |
| `api/users/me/notification-preferences` | ✅ | — | ✅ |

- Identity 版 `AuthController` 注释标注"**Identity BC，Task A3 返工 + 新建 9 端点**" → Identity 是返工新版
- **UserAuth 是一个未拆分的单体**：认证/账号职责已由 Identity 重建，用户资料职责已由 UserCenter 重建，
  但**两个新 BC 都未部署**
- **硬约束**：9 条路由重叠意味着 **Identity 与 UserAuth 不能同时对外暴露** ——
  同时上线会在网关/服务发现层打架。因此必须有一次明确的**切换动作**，而非灰度共存
- **连带工作量**：职责迁移必然涉及**数据迁移**（用户账号 → IdentityDb；地址/收藏/浏览/通知偏好 → UserCenterDb）

**▶ 这是路线 A 的下一个决策点（R1.1）**，见第 6 节。

## 3. 无论哪条路线都必做的公共工作

### 3.1 验签侧改造（19 个 BC + 网关）
- `WebApplicationExtensions.cs:140-157`：由「仅 HS256」改为**条件式双验签** ——
  当 `JWT_RSA_PUBLIC_KEY_PEM` 存在时追加 RSA 公钥校验，否则行为与现状完全一致
- `ApiGateway`：同样改造 `BuildValidationParameters()` 的调用点
- **顺序要求**：验签侧必须先于签发侧上线（否则签了 RSA 没人认）

### 3.2 密钥材料供给（当前完全缺失）
- 生成 RSA 密钥对（建议 2048 位起，与 `EnvironmentKms` 注释中的 openssl 示例一致）
- 私钥 PEM **只下发给签发方**；公钥 PEM 下发给所有验签方
- 落点：`deploy/helm/leno/templates/secret.yaml` 新增键 +
  `deploy/consul/kv-seed.json` 登记非敏感项（**私钥不走 KV**）
- 环境变量约定（代码已固定）：`JWT_RSA_PRIVATE_KEY_PEM` / `JWT_RSA_PUBLIC_KEY_PEM`

### 3.3 配置登记
- `JwtSigning:SigningMode` —— 每个验签方需明确自己的验签模式；
  签发方设 `Dual` 或 `Rs256`

## 4. 推荐推进顺序（以路线 A 为例，利用现成的 Dual 模式）

```
阶段 1  验签侧具备双验签能力（签 HS256 不变）
        ├─ WebApplicationExtensions + 网关：公钥存在时才启用 RS256 校验
        └─ 全量发布 → 零行为变化，可安全回归   ← 可立即开工

阶段 2  密钥供给落地
        ├─ 生成 RSA 密钥对，私钥→签发方、公钥→验签方
        └─ Helm Secret + kv-seed 登记

阶段 3  签发方切 Dual（签 RS256，验两者）
        └─ 观察窗口：确认所有验签方均能通过

阶段 4  验签方收缩为仅 RS256，移除 HS256 分支
        └─ 最后再清理 JwtTokenGenerator 的 HS256 路径
```

**阶段 1 与阶段 2 之间无强依赖，可并行。**

## 5. 风险清单

| 风险 | 说明 | 缓解 |
|------|------|------|
| **签发/验签不同步 → 全站 401** | 若先切签发再改验签，所有服务立即拒绝 token | 严格按「验签先行」顺序；用 Dual 窗口兜住 |
| **改了模式但没配密钥 → 签发直接抛异常** | `EnvironmentKms:59-65` PEM 为空即抛，登录会挂 | 密钥供给（阶段 2）先于模式切换（阶段 3） |
| 密钥轮换 | `JwtSigning:CurrentKeyId` 已预留版本化（默认 `key-v1`），`RsaJwtSigningService` 支持 KeyId header | 轮换时先并行下发新旧公钥，再切 CurrentKeyId |
| Identity 未部署 | 路线 A 的前置阻塞 | 需纳入 A3 排期 |
| 双签发并存 | 路线 B 的副作用：两套签名实现 | 优先 A；若选 B 需明确收敛时间点 |
| 端到端未验证 | 现有测试仅覆盖 `RsaJwtSigningService` 单元级（`RsaJwtSigningServiceTests`），**无签发↔验签跨服务集成验证** | 阶段 3 前补一次端到端（签发→网关→BC 全链路） |

### R1.1（当前阻塞项）UserAuth / Identity / UserCenter 三者如何收敛？

**背景**：UserAuth 单体同时承担认证与用户资料两类职责，两类都已被重建
（认证 → Identity，资料 → UserCenter），但两者均未部署；且 9 条路由与 UserAuth 逐字冲突，
**不能同时对外暴露**。

**三个选项：**

- **A-1（彻底拆分，与目标架构一致）**：UserAuth 退役 —— 认证/账号 → Identity，用户资料 → UserCenter
  - 优点：一次到位，三个 BC 职责清晰；Identity 上线即接管签发，RS256 路线 A 顺理成章
  - 代价：**两个服务都要部署** + **两侧数据迁移**（账号数据、地址/收藏/浏览/通知偏好数据）+ 路由切换
  - 需确认：`AdminRolesController`（`api/admin/roles`）归属谁？UserAuth 独有，Identity/UserCenter 都没有

- **A-2（先只迁认证）**：认证/账号 → Identity；UserAuth 保留用户资料职责（暂不迁 UserCenter）
  - 优点：步子小，只部署一个服务，只需迁账号数据；RS256 可较快落地
  - 代价：UserAuth 留下"半单体"，4 条资料类路由仍在它身上；未来仍要再迁一次 UserCenter
  - 风险：需确保 UserAuth 与 Identity 的 `api/auth` 等 5 条路由**不同时暴露**（须走切换）

- **A-3（反向合并）**：不部署 Identity，把 Identity 的能力（RS256 / 2FA / OAuth / 密码栈）搬回 UserAuth，废弃 Identity
  - 优点：不动部署拓扑，改动集中在一个 BC
  - 代价：**须推翻路线 A 的决定**；产生大量代码搬移返工；UserCenter 的重叠仍未解
  - 何时考虑：若 Identity 部署在可预见期内无法排上

**决策所需的补充信息（需你提供）：**
1. **Identity 与 UserAuth 的目标关系**是"后者退役"还是"长期并存分工"？
2. **用户数据规模**：`LenoUserAuth` 库里账号/地址/收藏等数据量级（决定迁移方案是停机迁、双写还是按需迁）
3. **`api/admin/roles` 的归属**：归 Identity（权限在认证域）还是 AccessControl（独立 BC 已存在）？
4. **是否有客户端强依赖 UserAuth 的现状**：更换路由宿主对前端/第三方是否透明（网关层能否无感切换）？
