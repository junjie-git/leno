## A. 项目概述

### A.1 项目目标

Leno 是一个基于 DDD + CQRS + Event-Driven 的微服务电商平台。当前已实现核心基础功能，但存在大量缺失功能点。本项目目标是：

1. **补齐全部缺失功能**：按优先级完成所有 87 个任务
2. **建立完整测试体系**：为全部 11 个限界上下文创建测试项目，覆盖率 ≥ 80%
3. **完善基础设施**：对象存储、OpenTelemetry、配置中心、健康监控
4. **打通核心交易链路**：用户登录 → 商品浏览 → 加购 → 下单 → 支付 → 履约
5. **构建运营支撑体系**：数据看板、死信管理、索引重建、审计日志、限流配置

### A.2 项目范围

**包含模块（12 个）**：
- 共享内核 (Shared Kernel)
- BC1 用户与认证授权域 (user-auth)
- BC2 商品域 (product)
- BC3 购物车域 (cart)
- BC4 订单与交易域 (order)
- BC5 促销域 (promotion)
- BC6 支付集成域 (payment)
- BC7 积分与会员域 (points-membership)
- BC8 评价与售后域 (review-aftersales)
- BC9 卖家与店铺管理域 (seller-shop)
- BC10 消息通知域 (notification)
- BC11 系统管理域 (system-admin)

**不包含范围**：
- 前端 UI 开发
- 部署与运维自动化（CI/CD 管道已存在）
- 性能压测（仅代码层面优化）
- 第三方平台资质申请（微信/支付宝开发者账号）

| 容器化测试 | Testcontainers | 最新 |

### B.2 架构模式

- **DDD 分层架构**: Domain → Application → Infrastructure → API
- **CQRS**: 命令与查询职责分离
- **Event-Driven**: 跨域集成事件 + 领域事件
- **Outbox Pattern**: 发件箱模式保证事件投递可靠性
- **Adapter Pattern**: 支付渠道、通知渠道适配器

## C. 开发流程定义

### C.1 编码标准

**命名规范**:
- 聚合根: `{Entity}Aggregate` 或直接 `{Entity}`（如 `Order`、`User`）
- 值对象: `{Name}VO`（如 `AddressVO`、`PriceVO`）
- 仓储接口: `I{Entity}Repository`（如 `IOrderRepository`）
- 领域服务: `{ServiceName}DomainService`（如 `CartPricingDomainService`）
- 应用服务: `{ServiceName}AppService`（如 `OrderAppService`）
- DTO: `{Name}Dto`（如 `OrderDto`、`CreateOrderDto`）

**测试命名**:
- 方法命名: `Method_Scenario_ExpectedResult`（如 `Create_ValidOrder_ShouldPublishEvent`）
- 测试类命名: `{ClassName}Tests`（如 `OrderTests`）
- 测试集合命名: `{Module}Collection`（如 `OrderCollection`）

**代码质量要求**:
- 领域层测试覆盖率 ≥ 80%
- 应用层测试覆盖率 ≥ 70%
- API 层集成测试覆盖核心业务流程
- 禁止直接在控制器中编写业务逻辑
- 使用依赖注入，避免硬编码依赖

### C.2 版本控制策略

**分支命名**:
- `feature/{TaskId}-{description}`（如 `feature/SK-01-test-infrastructure`）
- `bugfix/{TaskId}-{description}`（如 `bugfix/ORD-02-lua-script-fix`）

**Commit 消息格式**:
```
[{TaskId}] {Action} {Description}

{Details}
```

示例:
```
[SK-01] Implement test infrastructure for all BCs

- Created xUnit test projects for 11 bounded contexts
- Configured Testcontainers for SQL Server, Redis, RabbitMQ, ES
- Set up Collection Fixtures for shared container instances
```

**PR 提交要求**:
- 每个 PR 对应一个任务（Task）
- PR 描述包含任务 ID、Checklist 完成状态、测试结果
- 必须通过 CI 流水线（构建 + 测试）才能合并

### C.3 测试要求

**单元测试**:
- 使用 xUnit + Moq + FluentAssertions
- 覆盖正常路径、边界条件、异常路径
- 领域层聚合方法必须有测试

**集成测试**:
- 使用 Testcontainers 启动真实依赖
- 覆盖 API 端点鉴权与权限校验
- 覆盖事件发布与消费流程

**测试执行**:
- 本地运行: `dotnet test --filter FullyQualifiedName!~Integration`（单元测试）
- 完整测试: `dotnet test`（含集成测试）
- CI 流水线自动运行全部测试

## D. Agent 架构设计

### D.1 Master Agent 职责

Master Agent 作为全局编排者，负责：

1. **任务调度**: 读取 `progress.md`，识别可执行任务（依赖已就绪）
2. **资源分配**: 根据任务类型创建专用子 Agent
3. **进度跟踪**: 实时更新任务状态到 `progress.md`
4. **质量把控**: 验证子 Agent 交付物（代码审查、测试通过）
5. **异常处理**: 处理失败任务，决定重试或换策略
6. **依赖管理**: 确保任务按依赖顺序执行

### D.2 子 Agent 类型

| Agent 类型 | 职责 | 适用场景 |
|-----------|------|----------|
| **Coding Agent** | 编写业务代码 | 实现聚合方法、应用服务、API 控制器 |
| **Test Agent** | 编写测试代码 | 创建测试项目、编写单元测试、集成测试 |
| **Infrastructure Agent** | 实现基础设施 | 对接第三方服务（支付、存储、消息队列） |
| **Event Agent** | 实现事件驱动 | 创建消费者、发布者、集成事件 |
| **Review Agent** | 代码审查 | 验证代码质量、测试覆盖率、编码规范 |

### D.3 交互机制

```
Master Agent
    │
    ├── 读取 progress.md → 分析依赖 → 选择下一个可执行任务
    │
    ├── 创建子 Agent → 分配任务 → 等待执行完成
    │
    ├── 验证交付物 → 更新进度 → 进入下一轮
    │
    └── 失败处理 → 重试/换策略/升级
```

### D.4 决策层次

| 层级 | 决策内容 | 执行者 |
|------|---------|--------|
| L1 | 任务选择与排序 | Master Agent |
| L2 | 技术实现方案 | 子 Agent（按规范执行） |
| L3 | 代码实现细节 | 子 Agent |
| L4 | 测试验证 | Review Agent |
| L5 | 异常处理策略 | Master Agent |

## E. Master Agent 功能定义

### E.1 全流程自主编排

**执行循环**:

```
WHILE 存在未完成任务 DO
    1. 读取 progress.md 获取所有任务状态
    2. 筛选可执行任务（状态=待开始 + 所有依赖已完成）
    3. 按优先级排序（P0 > P1 > P2）
    4. 选择最高优先级任务
    5. 创建对应子 Agent 执行任务
    6. 等待子 Agent 完成
    7. 验证交付物
    8. 更新任务状态
    9. 更新进度统计
END
```

**任务选择算法**:
- 优先选择 P0 任务
- 同一优先级按依赖链顺序
- 测试任务优先于业务任务（保障质量）
- 基础设施任务优先于业务任务（解除阻塞）

### E.2 进度跟踪系统

**状态更新规则**:
- 任务开始: 更新状态为 🔄 进行中，记录开始日期
- 任务完成: 更新状态为 ✅ 已完成，记录完成日期
- 任务失败: 更新状态为 ⏸️ 暂停，记录失败原因
- 任务取消: 更新状态为 ❌ 取消，记录取消原因

**统计更新**:
- 总任务数、已完成数、进行中数、待开始数
- 各模块完成率
- 整体完成率
- P0/P1/P2 完成分布

**报告生成**:
- 每日生成进度报告（控制台输出）
- 里程碑达成时生成阶段性报告
- 异常情况即时报告

### E.3 质量把控机制

**代码审查**:
- 检查命名规范是否符合标准
- 检查架构分层是否正确
- 检查依赖注入是否合理
- 检查异常处理是否完善

**测试验证**:
- 运行单元测试，验证覆盖率 ≥ 80%
- 运行集成测试，验证流程正确性
- 检查测试命名是否符合规范
- 检查测试覆盖是否全面（正常/边界/异常）

**质量评估**:
- 代码重复率检查
- 圈复杂度检查（方法 ≤ 15）
- 代码行数检查（类 ≤ 500）
- 接口文档完整性检查

### E.4 异常处理策略

**失败重试规则**:
- 技术原因失败（如编译错误、测试失败）: 最多重试 3 次
- 每次重试间隔: 指数退避（30s → 2min → 10min）
- 重试仍失败: 标记为暂停，记录失败原因，继续下一个任务

**升级机制**:
- 同一任务连续失败 3 次: 标记为 ⏸️ 暂停
- 关联任务全部失败: 检查是否存在系统性问题
- 基础设施任务失败: 优先修复，因其阻塞后续任务

**错误日志**:
- 记录失败任务 ID、失败原因、重试次数
- 记录环境信息（框架版本、依赖版本）
- 记录时间戳和上下文信息

## F. 子 Agent 管理规范

### F.1 任务分解原则

每个子任务必须满足：
- **可执行性**: 可在 1-2 个工作日内完成
- **独立性**: 无外部依赖或依赖已就绪
- **可测试性**: 有明确的验收标准
- **可提交性**: 产出可独立提交（单一 commit）

**Checklist 格式**:
```markdown
- [ ] {子任务描述}
- [ ] {子任务描述}
```

示例:
```markdown
- [ ] 创建 `StockReservationCacheService`
- [ ] 实现 Lua 脚本原子预占逻辑
- [ ] 集成到下单应用服务
- [ ] 编写单元测试
```

### F.2 子 Agent 生成标准

**Coding Agent**:
- 输入: 任务描述、技术实现路径、验收标准
- 输出: 完整代码实现（领域层 + 应用层 + API层）
- 验证: 代码可编译、测试通过

**Test Agent**:
- 输入: 目标测试项目、测试覆盖要求
- 输出: 测试代码、测试配置
- 验证: 测试通过率 100%

**Infrastructure Agent**:
- 输入: 第三方服务规格、API 文档
- 输出: 适配器实现、配置类、DI 注册
- 验证: 集成测试通过

**Event Agent**:
- 输入: 事件定义、消费逻辑、发布规则
- 输出: 事件类、消费者、发布者
- 验证: 事件消费端到端测试通过

**Review Agent**:
- 输入: 代码变更、测试结果
- 输出: 审查报告、改进建议
- 验证: 代码质量达标

### F.3 执行流程控制

**编码流程**:
1. 理解需求 → 设计方案 → 编写代码 → 编译验证
2. 先写领域层 → 再写应用层 → 最后写 API 层
3. 每个方法必须有单元测试

**测试流程**:
1. 创建测试项目 → 配置依赖 → 编写测试 → 运行测试
2. 先写单元测试 → 再写集成测试
3. 测试覆盖率必须达标

**文档流程**:
1. 更新任务文件 Checklist
2. 更新进度文档状态
3. 提交代码时包含变更说明

### F.4 成果交付要求

**代码提交**:
- 每个任务一个 commit（或相关任务一组 commit）
- commit 消息包含任务 ID 和描述
- 代码格式符合项目规范（dotnet format）

**测试报告**:
- 测试通过率（单元测试 + 集成测试）
- 测试覆盖率（领域层 ≥ 80%）
- 测试用例数量

**文档更新**:
- 更新 `tasks/{module}.md` 中对应任务的 Checklist
- 更新 `progress.md` 中任务状态和统计
- 如有架构变更，更新相关设计文档

**Checklist 验证**:
- 每个任务的子任务 Checklist 全部勾选才算完成

**测试验证**:

- **编译错误**: 代码语法问题，重试修复

- 编译错误: 根据错误信息自动修复
- 测试失败: 分析失败原因，修改代码
