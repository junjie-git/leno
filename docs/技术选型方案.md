## 1. 文档概述

### 1.1 文档背景

本电商平台采用领域驱动设计（DDD）方法论，将业务划分为 11 个限界上下文（Bounded Context），覆盖用户与认证授权、商品、购物车、订单与交易、促销、评价与售后、积分与会员、支付集成、消息通知、卖家与店铺管理、系统管理等核心与支撑域。需求文档集（00-12 共 13 篇）对各限界上下文的功能需求、领域模型、API 契约、集成事件、非功能指标做了详尽阐述。

为统一各团队的技术认知、避免选型碎片化、降低集成成本，有必要在工程实施前输出一份全局性的技术选型方案，明确运行时、框架、中间件、存储、安全、可观测性、部署等各维度的技术决策与依据，作为后续详细设计、编码、测试、部署的基准。

### 1.2 文档目标

本方案旨在达成以下目标：

1. **统一技术基准**：明确 .NET 10 + EF Core + DDD + CQRS + 消息队列 + 事件总线这一技术基准，并细化到具体组件、版本与配置。
2. **澄清选型理由**：对每一项关键技术给出选型理由、备选方案对比，形成可追溯的决策依据。
3. **指导落地实施**：为 11 个限界上下文提供技术落点清单，明确各上下文的存储、缓存、消息、外部集成策略。
4. **保障非功能指标**：将性能、安全、可用性、可扩展性、可观测性等非功能需求映射到具体技术手段。
5. **识别风险与演进**：识别关键技术风险并给出缓解措施，规划技术演进路线。

### 1.3 适用范围

本方案适用于电商平台全部 11 个限界上下文的技术实现，覆盖从领域层、应用层、基础设施层到表现层的完整技术栈。具体适用对象包括：

- 架构师与技术负责人：作为架构评审与决策依据。
- 后端开发工程师：作为编码规范、组件选型、配置管理的参考。
- 测试与运维工程师：作为环境搭建、部署编排、监控配置的依据。
- 新成员：作为快速了解平台技术全貌的入门文档。

## 2. 总体技术架构

### 2.1 架构风格总览

本平台采用 **DDD 限界上下文 + 模块化部署** 的架构风格，在逻辑上以限界上下文为边界组织代码与团队，在物理上以"角色端 × 上下文"为单元独立打包部署。整体架构遵循以下原则：

- **高内聚低耦合**：限界上下文内部高内聚，上下文之间通过集成事件（发布订阅）与防腐层（ACL）协作，禁止跨上下文直接共享数据库表。
- **读写分离（CQRS）**：写侧使用关系型数据库保证 ACID，读侧使用 Elasticsearch + Redis 提升查询性能与扩展性。
- **最终一致性优先**：跨上下文协作以集成事件驱动，容忍秒级最终一致性；强一致场景（如库存预占）在单一上下文内以 Redis Lua 脚本原子完成。
- **外部能力可替换**：支付、通知、文件存储等外部能力以接口抽象 + 配置注入方式接入，切换服务商不影响领域逻辑。
- **模块独立演进**：买家端、卖家端、运营端、系统管理端各自独立部署、独立扩缩容、独立发布回滚。

架构风格定位为"可演进的模块化单体/微服务"：初期各上下文可部署于同一进程（模块化单体）以降低运维复杂度，待流量与团队规模增长后，可沿限界上下文边界平滑拆分为独立微服务，得益于严格的上下文边界与事件驱动协作，拆分成本可控。

### 2.2 DDD 分层架构

平台严格遵循 DDD 四层架构，依赖方向为"表现层 → 应用层 → 领域层 ← 基础设施层"，领域层处于依赖倒置的核心位置，不引用任何外层。

```
┌─────────────────────────────────────────────────────────────┐
│                     表现层 (API Layer)                        │
│   Controllers / Filters / Middleware / DTO(输入输出)         │
│   按角色拆分: 买家端 / 卖家端 / 运营端 / 系统管理端          │
└──────────────────────────┬──────────────────────────────────┘
                           │ 依赖
┌──────────────────────────▼──────────────────────────────────┐
│                    应用层 (Application Layer)                │
│   ApplicationService / Command / Query / DTO / 事务编排      │
│   输入验证 / 安全认证 / 事件发布(经Outbox)                   │
└──────────────────────────┬──────────────────────────────────┘
                           │ 依赖
┌──────────────────────────▼──────────────────────────────────┐
│                    领域层 (Domain Layer)                     │
│   Entity / ValueObject / Aggregate / DomainService           │
│   IRepository(接口) / IDomainEvent / 领域规则                │
│   不引用基础设施层、应用层、表现层                            │
└──────────────────────────▲──────────────────────────────────┘
                           │ 实现(依赖倒置)
┌──────────────────────────┴──────────────────────────────────┐
│                基础设施层 (Infrastructure Layer)              │
│   Persistence / Messaging / Caching / Storage                │
│   Payment / Notification 适配器 / 工作单元实现                │
└─────────────────────────────────────────────────────────────┘
```

各层职责与规范：

| 层 | 职责 | 关键规范 |
|----|------|----------|
| 领域层 | 表达业务核心：实体、值对象、聚合根、领域服务、仓储接口、领域事件 | 不引用基础设施、应用、表现层；业务规则集中于此；聚合内保证一致性 |
| 应用层 | 任务编排、事务管理、输入验证、安全认证、事件发布 | 本身很薄，不含业务规则；通过仓储与领域服务协作；命令/查询分离 |
| 基础设施层 | 仓储实现、工作单元、消息发布、缓存、文件存储、支付/通知适配 | 按 Persistence、Messaging、Caching、Storage、Payment、Notification 子目录组织 |
| 表现层 | 控制器、过滤器、中间件、DTO 转换 | 控制器不含业务逻辑；RESTful 风格；输入输出一律使用 DTO；按角色拆分独立部署单元 |

### 2.3 CQRS 读写分离架构

平台采用 CQRS 模式将"命令（写）"与"查询（读）"在模型与物理存储上分离，以兼顾事务一致性与查询性能。

```
        ┌──────────── 命令侧 (Command) ────────────┐
  请求 ──▶│  ApplicationService                      │
        │     │ (事务 + Outbox)                       │
        │     ▼                                      │
        │  EF Core ──▶ 关系型写库 (SQL Server/PG)    │  保证 ACID
        │     │                                      │
        │     ▼ Outbox 表 (同事务)                    │
        └─────┼──────────────────────────────────────┘
              │ 后台轮询发布
              ▼
        ┌──── 事件总线 (RabbitMQ) ───────────────────┐
              │ 订阅                                  │
              ▼                                       │
        ┌──── 查询侧同步器 ────┐                      │
        │  消费事件 → 扁平化 →  │                    │
        │  写入 ES 读库         │                    │
        └──────────┬───────────┘                     │
                   ▼                                  │
        ┌──────── 查询侧 (Query) ────────────────────┐
  请求 ──▶│  QueryService                            │
        │     ├──▶ Elasticsearch (复杂搜索/列表)     │  95% < 500ms
        │     └──▶ Redis 缓存 (热点/明细)            │  复杂搜索 < 800ms
        └───────────────────────────────────────────┘
```

CQRS 关键设计要点：

1. **写库**：每个限界上下文使用独立 Schema 或独立库，通过 EF Core Code First 管理迁移，保证聚合持久化的 ACID。
2. **读库**：Elasticsearch 存储扁平化文档（如商品索引、订单查询视图），支持中文分词与复杂聚合查询；Redis 作为读侧二级缓存，承载热点明细与会话数据。
3. **同步机制**：写库变更产生领域事件，经发件箱表与事件总线发布，查询侧同步器消费事件并更新 ES 读库，实现最终一致性（秒级延迟）。
4. **强一致补强**：库存预占等强一致操作不走最终一致，而在命令侧以 Redis Lua 脚本原子完成预占，订单确认后再扣减写库。
5. **延迟与定时任务**：订单超时取消、积分清零、会员等级刷新等由 MQ 延迟消息或调度器驱动，避免轮询数据库。

### 2.4 事件驱动架构与发件箱模式

跨上下文协作以事件驱动为主。平台定义了 27+ 集成事件，包括 `UserRegisteredEvent`、`ProductPublishedEvent`、`OrderCreatedEvent`、`OrderPaidEvent`、`OrderCancelledEvent`、`OrderCompletedEvent`、`PaymentRequestedIntegrationEvent`、`PaymentSucceededIntegrationEvent`、`PaymentFailedIntegrationEvent`、`RefundRequestedIntegrationEvent`、`RefundSucceededIntegrationEvent`、`PointsEarnedEvent`、`PointsConsumedEvent`、`MemberLevelChangedEvent`、`ReviewApprovedEvent`、`RefundCompletedEvent`、`ShopSuspendedEvent`、`ShopClosedEvent` 等。

**发件箱模式（Outbox Pattern）** 保证数据库事务与消息发布的原子性，避免"事务提交但消息丢失"或"消息发送但事务回滚"的不一致：

```
┌─────────────── 命令处理（单一事务） ───────────────┐
│  1. 加载聚合根，执行业务方法                       │
│  2. 聚合产生领域事件                               │
│  3. EF Core SaveChanges:                          │
│       - 写入聚合状态变更                            │
│       - 写入 Outbox 表(同事务, 状态=待发布)         │
│  4. 提交事务                                       │
└────────────────────┬───────────────────────────────┘
                     │ (事务外, 异步)
┌────────────────────▼───────────────────────────────┐
│  Outbox 后台进程(轮询, 每 N 秒):                    │
│   - 查询 Outbox 表待发布记录                       │
│   - 发布到 RabbitMQ                               │
│   - 标记为已发布(或删除)                            │
│   - 失败重试, 超阈值进入死信队列                     │
└────────────────────────────────────────────────────┘
```

Outbox 表结构示例：

```sql
CREATE TABLE OutboxMessages (
    Id              UNIQUEIDENTIFIER PRIMARY KEY,
    OccurredOn      DATETIME2 NOT NULL,
    Type            NVARCHAR(256) NOT NULL,    -- 事件类型全名
    Payload         NVARCHAR(MAX) NOT NULL,    -- JSON 序列化的事件体
    AggregateId     UNIQUEIDENTIFIER NOT NULL,
    Status          TINYINT NOT NULL DEFAULT 0,-- 0=待发布 1=已发布 2=失败
    RetryCount      INT NOT NULL DEFAULT 0,
    ProcessedOn     DATETIME2 NULL
);
```

**消费侧的幂等与重试**：消费者通过事件 Id + 业务唯一键实现幂等（如订单号去重）；消费失败按指数退避重试，超过最大次数进入死信队列（DLQ），由系统管理域的死信队列管理功能人工介入或自动补偿。

### 2.5 共享内核设计

平台提取跨上下文共享的稳定契约至共享内核（Shared Kernel），避免重复定义与不一致。共享内核内容：

| 共享元素 | 说明 |
|----------|------|
| Money 值对象 | 金额与币种，四舍五入到两位小数，所有金额字段统一使用 |
| 身份标识 | 全局使用 GUID 作为聚合标识，便于分布式生成与合并 |
| 集成事件契约 | 27+ 集成事件的接口与 DTO 定义，版本化演进 |
| 审计字段 | 创建时间、更新时间、操作人，由基类统一维护 |
| IExternalChannelOptions | 外部渠道（支付/通知）配置抽象 |
| IFileStorageService | 文件存储抽象接口 |

```csharp
// 共享内核：Money 值对象
public sealed class Money : ValueObject
{
    public decimal Amount { get; }
    public string Currency { get; }   // ISO 4217, 如 CNY

    public Money(decimal amount, string currency = "CNY")
    {
        Amount = Math.Round(amount, 2, MidpointRounding.AwayFromZero);
        Currency = currency;
    }
    // 算术运算、比较、相等性重写略
}

// 共享内核：审计基类
public abstract class AuditableEntity
{
    public DateTime CreatedAt { get; set; } = DateTime.UtcNow;
    public DateTime? UpdatedAt { get; set; }
    public string? Operator { get; set; }
}
```

共享内核的演进遵循"只增不改、破坏性变更需协商"原则，由架构组统一管控。

## 3. 核心技术栈选型

本章按类别梳理平台核心技术栈，对每一项关键技术给出选型理由、备选方案对比与配置示例。技术选型总览如下表：

### 3.1 运行时与框架

#### 3.1.1 .NET 10 运行时与 ASP.NET Core

| 维度 | 选定方案 | 备选方案 |
|------|----------|----------|
| 运行时 | .NET 10 | Java 17/Spring、Node.js、Go |
| Web 框架 | ASP.NET Core 10 Web API | Spring Boot、NestJS、Gin |

**选型理由**：

- **性能领先**：.NET 10 在 TechEmpower 基准测试中吞吐与延迟表现处于第一梯队，AOT 编译与 JIT 优化成熟，契合订单创建 1000 TPS、秒杀 5000 QPS 的性能目标。
- **生态完备**：EF Core、ASP.NET Core Identity、内置依赖注入、配置系统、日志抽象等开箱即用，减少第三方依赖。
- **跨平台与容器友好**：官方镜像体积小（可使用 Alpine 变体），启动快，适合容器化与 K8s 部署。
- **团队技能匹配**：团队具备 .NET 技术栈积累，学习成本与招聘成本可控。
- **长期支持**：.NET 10 为 LTS 版本，保障生产稳定性。

**备选方案对比**：Java/Spring 生态成熟、人才储备广，但内存占用与启动速度劣于 .NET；Node.js 在 I/O 密集场景优秀但 CPU 密集型计算与强类型约束较弱；Go 并发与部署优秀但 ORM 与领域建模生态相对薄弱。综合性能、生态与团队因素，选择 .NET 10。

**按角色拆分独立 API 项目**：表现层按角色拆分为买家端、卖家端、运营端、系统管理端独立 ASP.NET Core 项目，各自独立部署、独立扩缩容、独立鉴权策略，避免单一 API 承载全部职责导致的膨胀与安全暴露面过大。

配置示例（`Program.cs` 标准 Web API 管道）：

```csharp
var builder = WebApplication.CreateBuilder(args);

// EF Core + 分库连接
builder.Services.AddDbContext<OrderDbContext>(opt =>
    opt.UseSqlServer(builder.Configuration.GetConnectionString("OrderDb")));

// JWT 认证
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(opt =>
    {
        opt.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = true,
            ValidateAudience = true,
            ValidateLifetime = true,
            ValidateIssuerSigningKey = true,
            ValidIssuer = builder.Configuration["Jwt:Issuer"],
            ValidAudience = builder.Configuration["Jwt:Audience"],
            IssuerSigningKey = new SymmetricSecurityKey(
                Encoding.UTF8.GetBytes(builder.Configuration["Jwt:Key"]!))
        };
    });

// Swagger
builder.Services.AddEndpointsApiExplorer();
builder.Services.AddSwaggerGen();

// 限流(滑动窗口 Redis)
builder.Services.AddSingleton<IRateLimiter, RedisSlidingWindowRateLimiter>();

var app = builder.Build();

if (app.Environment.IsDevelopment())
{
    app.UseSwagger();
    app.UseSwaggerUI();
}

app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();
app.Run();
```

#### 3.1.2 ORM：EF Core 10

| 维度 | 选定方案 | 备选方案 |
|------|----------|----------|
| ORM | EF Core 10（Code First） | Dapper、NHibernate、RepoDB |

**选型理由**：

- **Code First + Migrations**：以代码定义模型，迁移脚本化执行，契合"各上下文迁移独立"的需求，便于 CI/CD 与多环境管理。
- **聚合持久化友好**：通过 Fluent API 配置聚合映射，仓储模式封装持久化细节，符合 DDD 仓储接口在领域层、实现在基础设施层的规范。
- **LINQ 表达能力**：复杂查询以强类型 LINQ 表达，降低 SQL 拼接错误。
- **事务与并发控制**：原生支持事务、乐观并发（RowVersion）、级联策略，满足订单状态机、库存扣减的并发场景。

**备选方案对比**：Dapper 性能更高但需手写 SQL，领域模型映射与迁移管理需自行封装，DDD 落地成本高；NHibernate 功能强大但配置复杂、社区活跃度下降。EF Core 在生产力与性能间取得最佳平衡，故选之。对于读侧高频查询，结合 Dapper 做轻量读模型查询作为补充（查询侧主要走 ES，故 EF Core 主要用于命令侧）。

#### 3.1.3 API 文档：Swagger / OpenAPI

采用 Swashbuckle 生成 OpenAPI 文档，开发环境提供 Swagger UI，便于前后端联调与接口契约治理。所有接口统一 RESTful 风格，资源名词复数命名，统一响应结构（`code`/`message`/`data`）。

### 3.2 数据存储

#### 3.2.1 写库（Command 侧）：SQL Server / PostgreSQL

| 维度 | 选定方案 | 备选方案 |
|------|----------|----------|
| 关系型写库 | SQL Server 2019 或 PostgreSQL | MySQL、Oracle |

**选型理由**：

- **ACID 与事务**：命令侧首要保证强一致性，关系型数据库的事务、行锁、隔离级别满足订单、支付、库存等核心写操作。
- **按上下文分库/分 Schema**：每个限界上下文独立 Schema 或独立库，物理隔离上下文数据，禁止跨上下文直接表关联，强制通过集成事件协作。
- **EF Core 支持完善**：SQL Server 与 PostgreSQL 均为 EF Core 一等公民 Provider，迁移与配置成熟。
- **双选策略**：SQL Server 适合已有微软生态授权的部署；PostgreSQL 开源免费、JSONB 与扩展生态丰富，两者可按部署环境与成本择一。文档约定默认 SQL Server，PostgreSQL 为等价备选。

**备选方案对比**：MySQL 在互联网领域应用广泛，但 EF Core 对 SQL Server/PG 的特性支持更完善（如序列、JSONB、行版本），且 SQL Server/PG 的事务与锁机制在高并发订单场景更稳健。Oracle 成本高且重，不纳入。

**分库策略**：

| 限界上下文 | 写库 | 说明 |
|------------|------|------|
| BC1 用户与认证 | UserDb | 账户、角色、地址 |
| BC2 商品 | ProductDb | SPU/SKU、分类品牌 |
| BC4 订单 | OrderDb | 订单聚合、状态机 |
| BC5 促销 | PromotionDb | 优惠券、秒杀、满减 |
| BC7 积分与会员 | MemberDb | 积分账户、会员等级 |
| BC8 支付 | PaymentDb | 支付单、对账 |
| 其他上下文 | 各自独立 Schema/库 | 同理 |

#### 3.2.2 数据库迁移管理

EF Core Migrations 脚本化执行，各上下文迁移独立，禁止跨上下文共享迁移。迁移脚本纳入版本控制，CI 流水线自动生成并执行。

```bash
# 各上下文独立迁移命令示例
dotnet ef migrations add InitOrder -c OrderDbContext -p src/Order.Infrastructure -s src/Order.API
dotnet ef database update -c OrderDbContext -p src/Order.Infrastructure -s src/Order.API
```

迁移规范：仅追加式变更（Add Column），破坏性变更（Drop/Rename）分多版本灰度，避免停机与数据丢失。

### 3.3 缓存与搜索

#### 3.3.1 缓存：Redis

| 维度 | 选定方案 | 备选方案 |
|------|----------|----------|
| 分布式缓存 | Redis | Memcached、本地内存缓存 |

**选型理由**：

- **数据结构丰富**：String、Hash、List、Set、ZSet、Stream，可承载会话、购物车、库存预占、限流计数、积分余额等异构场景。
- **Lua 脚本原子性**：库存预占等强一致操作以 Lua 脚本在单线程内原子执行，避免竞态。
- **过期与淘汰策略**：TTL 过期 + LRU 淘汰，适合热点缓存与会话管理。
- **持久化与高可用**：RDB/AOF 持久化 + Sentinel/Cluster 高可用，满足生产要求。

**Redis 在各场景的用法**：

| 用途 | 数据结构 | 说明 |
|------|----------|------|
| 会话/Token | String + TTL | JWT Refresh Token、登录态 |
| 临时购物车 | Hash | 匿名购物车，登录后与用户购物车合并 |
| 库存预占 | String/Lua | 秒杀库存原子预占 |
| 限流计数 | ZSet/String | 滑动窗口限流 |
| 积分余额缓存 | String | 热点账户余额缓存 |
| 商品/促销热点 | String/Hash | 详情页缓存，降低 DB 压力 |

**库存预占 Lua 脚本示例**：

```lua
-- KEYS[1]=stock:sku:{skuId}  ARGV[1]=qty
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil then return -1 end          -- 库存键不存在
if stock < tonumber(ARGV[1]) then return 0 end -- 库存不足
redis.call('DECRBY', KEYS[1], ARGV[1])
return 1                                    -- 预占成功
```

#### 3.3.2 搜索引擎：Elasticsearch + NEST

| 维度 | 选定方案 | 备选方案 |
|------|----------|----------|
| 搜索/读库 | Elasticsearch 8.x + NEST | Solr、OpenSearch、数据库全文索引 |

**选型理由**：

- **读库（CQRS Query 侧）**：扁平化文档存储商品索引、订单查询视图，支持复杂搜索、聚合、排序，契合"复杂搜索 < 800ms"目标。
- **中文分词**：集成 `ik_smart` 中文分词器，保障商品标题、搜索关键词的中文分词质量。
- **横向扩展**：分片与副本机制支持海量数据与高并发查询，可独立扩缩容。
- **NEST 强类型客户端**：以强类型 Fluent API 构建查询，降低 JSON 拼接错误。

**备选方案对比**：Solr 功能相近但实时性与生态略逊；OpenSearch 为 ES 分支，兼容但社区分裂风险；数据库全文索引性能与功能无法满足电商搜索复杂度（ facets、打分、高亮）。选 Elasticsearch。

**商品索引扁平化文档示例**：

```json
{
  "spuId": "guid-001",
  "skuId": "guid-002",
  "title": "Apple iPhone 15 Pro 256GB",
  "categoryName": "手机数码",
  "brandName": "Apple",
  "price": 8999.00,
  "stock": 100,
  "attributes": { "color": "钛原色", "storage": "256GB" },
```

**ES 索引启动时检查与创建**：应用启动时检查索引存在性，缺失则创建并配置 `ik_smart` 分词器与分析器，避免手动维护。

```csharp
public async Task EnsureIndexExistsAsync(string indexName)
{
    var exists = await _client.Indices.ExistsAsync(indexName);
    if (!exists.Exists)
    {
        await _client.Indices.CreateAsync(indexName, c => c
            .Settings(s => s.Analysis(a => a
                .Analyzer(an => an.Custom("ik_smart_analyzer")
                    .Tokenizer("ik_smart"))))
            .Map<ProductDocument>(m => m.AutoMap()));
    }
}
```

### 3.4 消息与事件

#### 3.4.1 消息队列：RabbitMQ + MassTransit

| 维度 | 选定方案 | 备选方案 |
|------|----------|----------|
| 消息队列 | RabbitMQ + MassTransit | Kafka、Azure Service Bus、NATS |

**选型理由**：

- **Topic Exchange + 死信队列 + 延迟队列**：契合平台对集成事件路由、消费失败重试与死信、订单超时延迟任务的需求。
- **MassTransit 抽象**：以 `IEventBus` 接口封装发布订阅，屏蔽底层 MQ 差异，未来可平滑替换为其他传输（如 Kafka、Azure Service Bus）。
- **可靠投递与确认**： publisher confirm 与 consumer ack 机制保证消息不丢；配合发件箱模式实现至少一次（at-least-once）投递。
- **运维成熟**：RabbitMQ 管理界面、监控插件完善，社区与文档丰富。

**备选方案对比**：Kafka 吞吐极高但偏向日志流场景，延迟队列与路由灵活度不如 RabbitMQ，且运维成本高；Azure Service Bus 云绑定、有厂商锁定风险；NATS 轻量但持久化与事务支持弱。电商平台集成事件量级（非海量日志流）与路由/延迟需求更匹配 RabbitMQ，故选之。若未来日志型高频事件增多，可引入 Kafka 作为补充通道。

**Exchange / Queue / Binding 启动时声明**：应用启动时自动声明 Exchange、Queue、Binding 与死信 Exchange，确保拓扑一致。

**RabbitMQ 拓扑设计**：

| 元素 | 命名 | 说明 |
|------|------|------|
| Topic Exchange | `ecommerce.events` | 所有集成事件发布到此 |
| 业务队列 | `q.{consumer}.{event}` | 按消费者 × 事件绑定，如 `q.payment.order-created` |
| 死信 Exchange | `ecommerce.events.dlx` | 消费失败消息转入 |
| 死信队列 | `q.dlq.{consumer}` | 死信存储，供人工/补偿处理 |
| 延迟队列 | 通过 DLX + TTL 实现 | 订单超时取消等延迟任务 |

#### 3.4.2 事件总线：IEventBus

事件总线以接口抽象于共享内核，基础设施层基于 MassTransit 实现，统一处理领域事件转集成事件的发布与订阅。

```csharp
// 共享内核：事件总线抽象
public interface IEventBus
{
    Task PublishAsync<TIntegrationEvent>(TIntegrationEvent @event,
        CancellationToken ct = default) where TIntegrationEvent : IntegrationEvent;
}

// 集成事件基类
public abstract record IntegrationEvent
{
    public Guid Id { get; init; } = Guid.NewGuid();
    public DateTime OccurredOn { get; init; } = DateTime.UtcNow;
    public string EventType => GetType().Name;
}

// 订单创建集成事件
public record OrderCreatedIntegrationEvent(
    Guid OrderId, Guid UserId, decimal TotalAmount, string Currency,
    IEnumerable<OrderItemDto> Items) : IntegrationEvent;
```

消费者通过 MassTransit 的 `IConsumer<T>` 实现，结合幂等校验（事件 Id 去重）与重试策略（指数退避 + 死信）保障可靠消费。

### 3.5 认证与安全

#### 3.5.1 认证授权：JWT + OAuth2

| 维度 | 选定方案 | 备选方案 |
|------|----------|----------|
| 令牌 | JWT（Access 2h / Refresh 7d） | Session Cookie、Opaque Token |
| OAuth2 | OpenIddict / AspNet.Security.OAuth.Providers | IdentityServer4、自研 |
| 密码哈希 | bcrypt | PBKDF2、Argon2 |

**选型理由**：

- **JWT 无状态**：Access Token 有效期 2 小时，Refresh Token 7 天，服务端无状态校验签名即可，适合多端与水平扩展；Refresh Token 存 Redis 便于吊销。
- **OAuth2 第三方登录**：通过 AspNet.Security.OAuth.Providers 接入微信、QQ 等第三方登录，`state` 参数防 CSRF。
- **OpenIddict**：作为 OAuth2/OpenID Connect 服务端，支持授权码、客户端凭据等流程，开源且与 ASP.NET Core 集成紧密。
- **bcrypt 哈希**：自适应成本因子，抵御暴力破解与彩虹表。

**备选方案对比**：Session Cookie 有状态不利于多端与扩展；IdentityServer4 已转商业许可（Duende），社区版维护受限；OpenIddict 开源免费、社区活跃，更优。Argon2 比 bcrypt 更现代，但 bcrypt 生态成熟、实现广泛，二者均满足要求，默认 bcrypt。

**JWT 配置示例**：

```json
// appsettings.json
{
  "Jwt": {
    "Issuer": "ecommerce-auth",
    "Audience": "ecommerce-api",
    "Key": "<256-bit-secret>",
    "AccessTokenMinutes": 120,
    "RefreshTokenDays": 7
  },
  "OAuth2": {
    "WeChat": { "ClientId": "...", "ClientSecret": "...", "UseState": true }
  }
}
```

#### 3.5.2 限流：Redis 滑动窗口

| 维度 | 选定方案 | 备选方案 |
|------|----------|----------|
| 限流 | Redis 滑动窗口计数 | 固定窗口、令牌桶（客户端） |

秒杀等高并发接口通过 Redis 滑动窗口限流，限制单用户/IP/接口的请求频率，超过阈值返回 429。系统管理域提供接口限流配置（BC11），支持动态调整。

#### 3.5.3 支付回调验签

微信支付、支付宝回调均需验签：使用平台公钥/密钥校验签名，防止伪造回调。验签通过后再更新支付单状态，保证支付安全。

### 3.6 外部集成

外部集成遵循"领域层定义抽象接口、基础设施层提供适配器实现、参数配置化注入"原则，实现外部能力可替换。

#### 3.6.1 支付渠道：微信支付 + 支付宝

| 维度 | 选定方案 | 备选方案 |
|------|----------|----------|
| 支付渠道 | 微信支付 SDK + 支付宝 SDK | 聚合支付（Ping++）、自研对接 |

**选型理由**：

- **`IPaymentChannel` 适配**：领域层定义 `IPaymentChannel` 抽象（发起支付、查询、退款、回调验签），基础设施层提供 `WeChatPayChannel`、`AlipayChannel` 实现。
- **参数配置化**： appId、商户号、密钥、证书等参数从 appsettings.json / 配置中心注入，切换商户或新增渠道只需新增适配器并改配置。
- **直连主流渠道**：直接对接微信/支付宝官方 SDK，避免聚合支付中间层费用与依赖，掌握全链路控制。

```csharp
// 领域层抽象
public interface IPaymentChannel
{
    Task<PaymentResult> CreatePaymentAsync(PaymentRequest request, CancellationToken ct);
    Task<RefundResult> RefundAsync(RefundRequest request, CancellationToken ct);
    Task<bool> VerifyCallbackAsync(string rawBody, string signature);
}

// 基础设施层适配器(示意)
public class WeChatPayChannel : IPaymentChannel { /* 微信支付 SDK 封装 */ }
public class AlipayChannel : IPaymentChannel { /* 支付宝 SDK 封装 */ }
```

#### 3.6.2 通知渠道：邮件（SMTP）+ 短信

| 维度 | 选定方案 | 备选方案 |
|------|----------|----------|
| 邮件 | MailKit（SMTP） | System.Net.Mail（已过时）、SendGrid API |
| 短信 | 阿里云/腾讯云短信 SDK | 容联云、自研短信网关 |

**选型理由**：

- **`INotificationChannel` 适配**：消息通知域定义通知渠道抽象，邮件用 `IEmailChannel`、短信用 `ISmsChannel`，基础设施层提供 MailKit 与阿里云/腾讯云适配器。
- **MailKit**：跨平台、性能优、维护活跃，替代已废弃的 `System.Net.Mail`。
- **短信服务商双备**：阿里云/腾讯云可按配置切换或主备，提升送达率。
- **参数配置化**：SMTP 主机、端口、账号、短信 AccessKey 等从配置注入，支持配置中心热更新。

```json
// appsettings.json
{
  "Notification": {
    "Email": {
      "SmtpHost": "smtp.example.com",
      "SmtpPort": 587,
      "UserName": "noreply@example.com",
      "Password": "<secret>",
      "UseSsl": true
    },
    "Sms": {
      "Provider": "Aliyun",
      "AccessKey": "...",
      "SecretKey": "...",
      "SignName": "电商平台"
    }
  }
}
```

通知发送记录持久化，失败按重试策略重试，超阈值进入死信，保障通知可达性。

### 3.7 文件存储

#### 3.7.1 IFileStorageService 抽象

| 维度 | 选定方案 | 备选方案 |
|------|----------|----------|
| 文件存储 | IFileStorageService（Local/MinIO/OSS） | 直接耦合云 SDK、自研 FTP |

**选型理由**：

- **抽象隔离**：`IFileStorageService` 定义于共享内核，屏蔽本地磁盘与对象存储差异，业务层无感知存储介质。

- **独立上传端点**：文件上传走独立端点 `POST /api/files/upload`（带 `category` 参数），返回 URL 后再提交业务请求，解耦文件与业务事务。

## 4. 各限界上下文技术落点

本章将技术栈映射到 11 个限界上下文，明确各上下文在存储、缓存、消息、外部集成等方面的技术落点。各上下文遵循统一的 DDD 分层与 CQRS 基准，下表仅列各上下文的差异化要点。

| 编号 | 限界上下文 | 类型 | 写库 | 读库/缓存 | 关键技术点 |
|------|-----------|------|------|-----------|-----------|
| BC1 | 用户与认证授权域 | 核心 | UserDb | Redis(Token/会话) | JWT/OAuth2、bcrypt、地址聚合 |
| BC2 | 商品域 | 核心 | ProductDb | ES商品索引+Redis | ik_smart分词、审核状态机、索引重建 |

| BC5 | 促销域 | 核心 | PromotionDb | Redis库存预减 | 秒杀Lua预减、限流、异步建单 |
| BC6 | 评价与售后域 | 核心 | ReviewDb | ES评价检索 | 售后单状态机、退款请求 |

### 4.1 BC1 用户与认证授权域（核心）

**核心职责**：账户生命周期、身份认证、权限授权、收货地址。

**技术落点**：

- **认证**：JWT（Access 2h / Refresh 7d，Refresh 存 Redis 便于吊销）+ OAuth2 第三方登录（微信/QQ，`state` 防 CSRF）。
- **密码安全**：bcrypt 哈希存储，登录失败次数 Redis 计数锁定。
- **写库**：UserDb（账户、角色权限、收货地址聚合）。
- **缓存**：Redis 存 Refresh Token、登录态、权限缓存（RBAC 角色权限缓存以降低鉴权 DB 查询）。
- **事件**：发布 `UserRegisteredEvent`（触发积分域发放新人积分与成长值档案）。
- **特殊点**：账户聚合封装生命周期（注册→激活→冻结→注销），收货地址作为独立聚合或账户内实体，地址默认值切换由聚合方法保证唯一性。

### 4.2 BC2 商品域（核心）

**核心职责**：SPU/SKU 建模、分类品牌、商品审核、搜索索引。

**技术落点**：

- **写库**：ProductDb（SPU/SKU 聚合、分类、品牌）。
- **读库**：Elasticsearch 商品索引（扁平化文档，集成 `ik_smart` 中文分词），承载搜索、列表、筛选、聚合。
- **缓存**：Redis 缓存商品详情、分类树、品牌列表等热点数据。
- **索引同步**：商品发布/审核通过产生 `ProductPublishedEvent`，经事件总线由查询侧同步器写入 ES；系统管理域（BC11）可触发全量索引重建。
- **审核状态机**：SPU 聚合封装审核状态流转（待审核→审核通过→已上架/下架），状态变更由聚合方法保证合法性。
- **特殊点**：SKU 价格与可售库存基线由商品域权威持有，秒杀活动库存独立于商品域可售库存基线，互不影响。

### 4.3 BC3 购物车域（核心）

**核心职责**：购物车聚合、匿名与登录合并、价格实时计算。

**技术落点**：

- **缓存优先**：Redis Hash 存储临时购物车（匿名用户以设备/会话 ID 为键），登录后与用户购物车合并。
- **写库**：CartDb 持久化登录用户购物车聚合。
- **价格实时计算**：购物车展示时实时查询商品域价格与促销域优惠试算（调用促销域试算接口或消费价格事件），不固化价格快照（价格以下单时刻为准）。
- **事件**：消费 `OrderCreatedEvent` 清空已结算购物车项。
- **特殊点**：匿名与登录购物车合并需处理 SKU 重复累加、失效商品剔除等规则，合并由应用层编排。

### 4.4 BC4 订单与交易域（核心）

**核心职责**：订单聚合、状态机、库存预占与扣减、发起支付请求。

**技术落点**：

- **聚合设计**：`Order` 聚合根（封装订单状态机与金额不变量）+ `StockReservation` 聚合根（库存预占按 SKU 独立聚合，承载高频台账）。支付单由 BC8 维护，本域仅保留支付结果快照。
- **库存原子操作**：`RedisInventoryRepository` 以 Lua 脚本完成预占/扣减/释放的原子操作（判余量+扣减+记录预占），避免并发超卖；商品域通过订阅库存事件同步可售库存基线。
- **多卖家拆单**：购物车结算涉及多卖家时，应用层按卖家拆分为多个 `Order` 聚合，支撑卖家按店铺履约。
- **延迟消息**：订单超时取消、支付超时、售后期结束等由 MQ 延迟消息驱动（`OrderTimeoutDelayMessageConsumer`），避免轮询数据库。
- **CQRS 读库**：`OrderReadModelSyncConsumer` 消费订单事件同步 ES 订单查询视图。
- **事件**：发布 `OrderCreatedEvent`（清购物车/预占库存/锁券/延迟取消/通知/ES同步）、`OrderPaidEvent`（触发券核销与满额赠）、`OrderCompletedEvent`（开放评价/标记待发积分/经营概览/售后期延迟）、`OrderCancelledEvent`（释放库存/退券/释放冻结积分）、`OrderAfterSalesWindowClosedEvent`（发放消费返积分）。
- **幂等**：下单接口通过 `Idempotency-Key` 头防重复下单。

### 4.5 BC5 促销域（核心）

**核心职责**：优惠券、限时秒杀、满减折扣。

**技术落点**：

- **秒杀高并发**：活动开始时将秒杀库存与每用户限购集合载入 Redis，秒杀接口以 Redis Lua 脚本原子执行 check-and-decrement（剩余>0 且用户未达限购才预减）；聚合的 AvailableStock 与 PreDeductedCount 由对账任务周期校正。秒杀限流走 Redis 滑动窗口。
- **领券高并发**：领券库存高并发计数走 Redis 原子预减（`RedisCouponStockStore`），成功后再持久化实例与聚合计数。
- **异步建单**：秒杀成功后 MQ 异步建单，促销域发布 `SeckillOrderCreatedEvent` 通知订单域落单，避免秒杀接口同步建单的阻塞。
- **写库**：PromotionDb（优惠券批次、秒杀活动、满减规则、满额赠规则）。
- **事件驱动**：消费 `OrderPaidEvent`（触发券核销与满额赠判断）、`RefundCompletedEvent`（触发券退还）、`OrderCancelledEvent`（触发券预占释放）、积分域 `PointsExchangeCouponRequestedEvent`（积分换券）。
- **过期任务**：过期优惠券/秒杀活动由调度器或延迟消息处理。

### 4.6 BC6 评价与售后域（核心）

**核心职责**：商品评价、退货退款售后单、发起退款请求。

**技术落点**：

- **写库**：ReviewDb（评价聚合、售后单聚合）。
- **读库**：ES 评价检索（按商品/评分聚合统计）。
- **售后单状态机**：聚合封装售后单流转（申请→审核→退款中→退款完成/拒绝），退款审核通过后发布 `RefundRequestedIntegrationEvent` 请求支付集成域退款。
- **事件**：发布 `ReviewApprovedEvent`（积分域发放评价积分）、`RefundCompletedEvent`（促销域退券、系统管理域统计）。
- **特殊点**：评价在订单完成后由 `OrderCompletedEvent` 开放，售后单与订单、退款通过 ID 引用协作。

### 4.7 BC7 积分与会员域（支撑）

**核心职责**：积分账户、成长值与会员等级、付费会员、积分流水、任务中心。

**技术落点**：

- **聚合设计**：`PointsAccount`（积分账户+流水同事务）、`GrowthProfile`（成长值档案+会员等级）、`PaidMembership`（付费会员）、`PointsTransaction`（不可变流水）、`TaskCenter`（任务记录）。
- **缓存**：Redis 缓存热点积分账户余额（`PointsEarnedEvent`/`PointsConsumedEvent` 更新缓存），降低高频余额查询 DB 压力。
- **定时任务**：积分清零（过期积分 `Expire`）、会员等级刷新（每月 1 日定级 `LastEvaluatedAt`）、付费会员到期前 30 天标记 `ExpiringSoon`，由调度器或延迟消息驱动。
- **事件**：消费 `UserRegisteredEvent`（发放新人积分与成长值档案）、`OrderAfterSalesWindowClosedEvent`（发放消费返积分与成长值）；发布 `PointsEarnedEvent`、`PointsConsumedEvent`、`MemberLevelChangedEvent`、`PaidMemberSubscribedEvent`。
- **特殊点**：积分余额可为负（退款扣回记 `NegativeOffset`），后续赚取先抵扣负余额；流水不可变用于审计。

### 4.8 BC8 支付集成域（支撑）

**核心职责**：支付单、微信/支付宝渠道适配、退款、回调验签、对账。

**技术落点**：

- **聚合设计**：`PaymentOrder`（支付单聚合）+ `RefundOrder`（退款单聚合），均封装状态机与渠道交互生命周期；累计退款上限由聚合方法保证。
- **渠道适配**：领域层定义 `IPaymentChannel` 抽象 + `ChannelCredential` 值对象 + `IExternalChannelOptions` 配置契约；基础设施层实现 `WeChatPayChannel`、`AlipayChannel`，参数从配置中心/appsettings.json 注入。
- **回调验签**：微信/支付宝回调使用平台公钥/密钥验签，验签后留存 `CallbackRaw` 原始报文便于对账排查；重复回调幂等返回成功。
- **对账**：对账文件解析在基础设施层，定时对账校正支付/退款状态差异。
- **事件**：消费订单域 `PaymentRequestedIntegrationEvent`（创建支付单）、售后域 `RefundRequestedIntegrationEvent`（创建退款单）；发布 `PaymentSucceededIntegrationEvent`、`PaymentFailedIntegrationEvent`、`RefundSucceededIntegrationEvent`、`RefundFailedIntegrationEvent`。
- **特殊点**：本域不持有订单/售后聚合，仅以 ID 与业务单号引用；订单应付金额、售后退款金额由上游传入。

### 4.9 BC9 消息通知域（通用子域）

**核心职责**：通知模板、邮件/短信渠道适配、发送记录、重试。

**技术落点**：

- **聚合设计**：`NotificationTemplate`（模板，配置类低频变更）+ `NotificationRecord`（发送记录，高频写入含状态机），二者独立聚合。
- **渠道适配**：`INotificationChannel`/`IEmailChannel`/`ISmsChannel` 抽象，基础设施层 MailKit（邮件）+ 阿里云/腾讯云（短信）适配器，参数配置化支持热更新。
- **模板渲染**：模板含变量定义与占位符，发送时以业务数据渲染并固化 `ContentSnapshot` 正文快照，防模板后续修改影响已发记录。
- **重试与死信**：发送失败按重试策略（`RetryCount`/`MaxRetry` 默认 3）重试，超阈值进入死信；含频率限制防骚扰。
- **事件**：消费各业务事件映射到通知模板编码后入队；发布 `NotificationSentEvent`、`NotificationFailedEvent`、`NotificationRetriedEvent`、`NotificationDeadLetteredEvent` 供可观测与统计。
- **特殊点**：统一收口全平台邮件/短信，发送过程不阻塞主交易链路（经发件箱异步发送）。

### 4.10 BC10 卖家与店铺管理域（支撑）

**核心职责**：卖家入驻审核、店铺信息与资质管理、店铺状态管理。

**技术落点**：

- **写库**：ShopDb（卖家账户、店铺信息、资质材料）。
- **缓存**：Redis 缓存店铺基础信息（买家端高频展示）。
- **文件存储**：资质材料（营业执照等）通过 `IFileStorageService` 上传，返回 URL 后关联店铺聚合。
- **入驻审核**：卖家入驻申请状态机（申请→审核→通过/驳回），审核通过激活店铺。
- **事件**：发布 `ShopSuspendedEvent`、`ShopClosedEvent`（通知订单域、商品域下架相关资源）；消费 `OrderCompletedEvent` 累计经营概览。

### 4.11 BC11 系统管理域（通用子域）

**核心职责**：数据看板统计、死信队列管理、索引重建、审计日志聚合、接口限流配置、系统健康监控。

**技术落点**：

- **只读统计聚合**：订阅各域集成事件（`OrderCreatedEvent`/`OrderPaidEvent`/`PaymentSucceededIntegrationEvent`/`PointsEarnedEvent`/`NotificationSentEvent`/`RefundCompletedEvent` 等）做统计聚合，以只读快照落地 `DashboardReport`，不反向写各域业务数据。
- **死信队列管理**：汇聚各 MQ 死信队列，统一查看/重投/丢弃（`DeadLetterMessage`），领域层只见抽象接口，基础设施层对接 RabbitMQ。
- **索引重建**：触发各域 ES 读库全量重建并跟踪进度（`IndexRebuildTask`/`RebuildStatus`），基础设施层对接 Elasticsearch。
- **限流配置**：针对 API 的限流阈值与算法配置（`RateLimitRule`），下发至各角色网关/Redis 限流计数。
- **审计日志聚合**：聚合跨域管理员关键操作（`AuditLogEntry`，不可篡改记录）。
- **健康监控**：聚合各模块 `/health` 端点状态，呼应可观测性；对接 Prometheus+Grafana 监控告警。
- **特殊点**：本域为管理操作入口，技术实现属基础设施层（MQ/ES/Redis 对接），领域层只见抽象接口，避免领域层耦合具体中间件。

## 5. 技术选型决策记录（ADR）

本章以架构决策记录（Architecture Decision Record, ADR）格式记录关键技术决策，便于追溯与评审。每条 ADR 包含：状态、背景、决策、理由、备选方案、后果。

### ADR-001：采用 .NET 10 + DDD + CQRS 作为技术基准

- **状态**：已接受
- **背景**：平台覆盖 11 个限界上下文、6 个核心域，业务复杂度高，需要既能表达领域复杂度又能支撑高并发的技术基准。团队具备 .NET 技术积累。
- **决策**：统一采用 .NET 10 + ASP.NET Core + EF Core，以 DDD 分层组织代码，以 CQRS 分离读写，以事件驱动协作跨上下文。
- **理由**：.NET 10 性能领先、生态完备、容器友好且为 LTS；DDD 应对业务复杂度；CQRS 兼顾事务一致性与查询性能。
- **备选方案**：Java/Spring（生态成熟但资源占用高）、Node.js（I/O 强但类型与领域建模弱）、Go（部署优但 ORM 生态弱）。
- **后果**：统一技术栈降低集成与招聘成本；需团队掌握 DDD/CQRS，有一定学习曲线；初期需投入建立分层脚手架与共享内核。

### ADR-002：读写物理分离的 CQRS（写 SQL Server/PG，读 Elasticsearch + Redis）

- **状态**：已接受
- **背景**：商品搜索、订单查询等读场景需复杂检索与高 QPS（秒杀限流后 5000 QPS、复杂搜索 < 800ms），而写场景需 ACID 保证订单与支付一致性。
- **决策**：命令侧用 EF Core + 关系型写库（按上下文分库），查询侧用 Elasticsearch 扁平化文档 + Redis 缓存；写库变更经事件总线同步读库，最终一致。
- **理由**：读写关注点不同，物理分离可独立扩缩容；ES 提供中文分词与复杂聚合；Redis 缓存热点降低延迟。
- **备选方案**：单库读写（简单但查询性能与扩展性受限）、CQRS 同库不同模型（妥协方案）。
- **后果**：读性能与扩展性大幅提升；引入读库同步延迟（秒级）与运维复杂度；需处理读库重建（BC11 索引重建）与数据一致性对账。

### ADR-003：发件箱模式保证事件与事务一致性

- **状态**：已接受
- **背景**：跨上下文协作依赖集成事件，若"事务提交但消息丢失"或"消息发送但事务回滚"将导致数据不一致。
- **决策**：聚合保存与事件记录在同一事务写入 Outbox 表，后台进程轮询发布到 MQ，消费失败重试与死信。
- **理由**：发件箱模式以本地事务保证原子性，避免分布式事务的复杂度与性能开销，实现可靠的至少一次投递。
- **备选方案**：分布式事务（2PC，性能差且 RabbitMQ 不支持）、事务发件箱的 CDC 替代（如 Debezier，引入额外组件）。
- **后果**：保证事件可靠发布；需维护 Outbox 表与后台轮询进程；消费者须实现幂等（事件 Id 去重）应对至少一次投递的重复。

### ADR-004：RabbitMQ + MassTransit 作为事件总线

- **状态**：已接受
- **背景**：平台 27+ 集成事件需发布订阅路由，且需死信队列与延迟队列支撑订单超时取消、积分清零等场景。
- **决策**：采用 RabbitMQ（Topic Exchange + DLX + TTL 延迟队列）+ MassTransit 抽象，以 `IEventBus` 接口封装。
- **理由**：RabbitMQ 路由灵活、延迟队列与死信原生支持、运维成熟；MassTransit 屏蔽底层，未来可平滑替换传输。
- **备选方案**：Kafka（吞吐高但偏日志流、延迟队列弱）、Azure Service Bus（云锁定）、NATS（持久化弱）。
- **后果**：满足路由与延迟需求；RabbitMQ 单机吞吐有限，超大规模需集群；事件量级若未来增长到日志流级别可引入 Kafka 补充。

### ADR-005：按角色端 × 限界上下文独立部署

- **状态**：已接受
- **背景**：买家端、卖家端、运营端、系统管理端的使用场景、流量特征、安全要求差异大，混部署导致膨胀与安全暴露面过大。
- **决策**：表现层按角色拆分为独立 ASP.NET Core 项目，各自独立 Docker 镜像、独立部署、独立扩缩容、独立发布回滚。
- **理由**：独立部署隔离故障与安全风险，按角色流量独立扩缩容，发布互不影响；契合模块化部署架构（文档 10）。
- **备选方案**：单一 API 网关聚合（简单但耦合）、微服务按上下文拆（初期过度设计）。
- **后果**：部署与运维单元清晰；多项目带来构建与配置重复，需共享内核与基础类库降低重复；跨角色共性逻辑抽至共享层。

### ADR-006：外部能力抽象与配置化（支付/通知/存储）

- **状态**：已接受
- **背景**：支付渠道（微信/支付宝）、通知渠道（邮件/短信）、文件存储（本地/对象存储）属可替换外部能力，直连将导致领域层耦合服务商。
- **决策**：领域层定义抽象接口（`IPaymentChannel`/`INotificationChannel`/`IFileStorageService`），基础设施层提供适配器实现，参数从配置中心/appsettings.json 注入，支持热更新。
- **理由**：抽象隔离使领域逻辑不依赖服务商；配置化使切换/新增服务商只需新增适配器并改配置，符合开闭原则。
- **备选方案**：直连 SDK（耦合重）、聚合支付中间层（费用与依赖）。
- **后果**：外部能力可替换、可扩展；需为每个服务商维护适配器；接口抽象需前瞻性设计以覆盖多服务商差异。

### ADR-007：库存预占采用 Redis Lua 脚本强一致

- **状态**：已接受
- **背景**：秒杀与高并发下单的库存预占需防超卖，跨上下文最终一致无法满足秒杀瞬间的强一致要求。
- **决策**：库存预占在命令侧以 Redis Lua 脚本原子完成（判余量+扣减+记录预占），订单确认后再扣减写库；聚合的库存基线由对账任务周期校正。
- **理由**：Redis 单线程 + Lua 原子性保证 check-and-decrement 不竞态，性能远高于数据库行锁；对账任务校正 Redis 与 DB 的最终一致。
- **备选方案**：数据库乐观锁（高并发下重试多、性能差）、分布式锁（粒度粗、吞吐低）。
- **后果**：秒杀防超卖且高性能；Redis 与 DB 双写需对账机制保证最终一致；Redis 故障需降级策略（如临时关闭秒杀或回退 DB 悲观锁）。

### ADR-008：模块化单体起步，可演进至微服务

- **状态**：已接受
- **背景**：初期团队规模与流量有限，直接微服务化带来运维与分布式复杂度过高；但未来需支持业务增长。
- **决策**：初期各上下文可部署于同一进程（模块化单体），严格保持限界上下文边界与事件驱动协作；待流量与团队增长后沿上下文边界平滑拆分为独立微服务。
- **理由**：严格的上下文边界与事件驱动协作使拆分成本可控；模块化单体降低初期运维复杂度与分布式事务需求。
- **备选方案**：初期即微服务（过度设计）、单体不分上下文（后续难拆）。
- **后果**：初期开发与部署简单；需纪律性保持上下文边界（禁跨上下文共享表/直接调用）；拆分时主要工作是将进程内事件总线替换为 MQ、将同库拆为独立库。

## 6. 非功能需求技术保障

本章将非功能需求指标映射到具体技术手段，确保架构选型能落地各项质量属性。

### 6.1 性能保障

| 指标 | 目标 | 技术保障 |
|------|------|----------|
| 订单创建 | 1000 TPS | EF Core 批量写 + 分库降低锁争用；库存预占走 Redis Lua（微秒级）；下单异步化非关键路径（通知、ES 同步经事件） |
| 秒杀接口 | 限流后 5000 QPS | Redis Lua 原子预减库存；Redis 滑动窗口限流；秒杀成功后 MQ 异步建单避免同步落库阻塞 |
| 通用 API | 95% 响应 < 500ms | 查询走 ES + Redis 缓存；写库索引优化；连接池复用；异步非阻塞 |
| 复杂搜索 | < 800ms | Elasticsearch 分片 + `ik_smart` 分词 + 查询 DSL 优化；热点结果 Redis 缓存 |

**性能保障手段详述**：

- **读写分离降低争用**：CQRS 使读流量走 ES/Redis，写流量走关系库，互不干扰，各自按负载扩缩容。
- **缓存分层**：Redis 作为一级缓存承载热点查询与会话，ES 作为读库承载复杂检索，DB 仅承载命令写。
- **异步化**：通知、读库同步、跨上下文协作均经事件总线异步，不阻塞主交易链路；秒杀建单 MQ 异步化。
- **原子操作**：库存预占、领券、限流计数以 Redis Lua 原子完成，避免锁等待与重试。
- **连接池与批处理**：EF Core 连接池复用；批量插入（如订单项）减少往返。

### 6.2 安全保障

| 安全需求 | 技术保障 |
|----------|----------|
| 身份认证 | JWT（Access 2h / Refresh 7d），Refresh 存 Redis 可吊销；OAuth2 第三方登录 `state` 防 CSRF |
| 密码存储 | bcrypt 哈希（自适应成本因子） |
| 接口鉴权 | `Authorization: Bearer {token}`；RBAC 角色权限缓存于 Redis |
| 限流防刷 | Redis 滑动窗口限流，单用户/IP/接口维度，超限返回 429 |
| 支付安全 | 微信/支付宝回调验签（公钥/密钥校验），验签后更新状态；CallbackRaw 留存 |
| 幂等防重 | `Idempotency-Key` 头防重复下单/支付；事件 Id 去重消费 |
| 传输安全 | 全站 HTTPS；敏感配置（密钥、证书）环境变量/配置中心注入，不入库不入仓 |
| 审计追溯 | 管理员关键操作审计日志（BC11 `AuditLogEntry`，不可篡改） |

### 6.3 可用性保障

| 可用性需求 | 技术保障 |
|------------|----------|
| 服务健康检测 | `/health` 端点按模块检测（DB/Redis/MQ/ES），供负载均衡探活与故障转移 |
| 消息可靠 | 发件箱模式保证事件不丢；消费失败重试 + 死信队列，死信由 BC11 管理/补偿 |
| 外部渠道容错 | 通知失败重试 + 死信；支付/通知渠道支持主备切换（如短信阿里云/腾讯云） |
| 数据持久 | Redis RDB/AOF 持久化 + 主从；数据库定期备份 + 主从复制 |
| 降级策略 | Redis 故障时库存预占降级（回退 DB 悲观锁或临时关闭秒杀）；ES 故障时读请求降级至 DB |

### 6.4 可扩展性保障

| 可扩展性需求 | 技术保障 |
|--------------|----------|
| 读写独立扩缩容 | Command 写库与 Query 读库物理分离，ES/Redis 可独立水平扩展 |
| 模块独立部署 | 买家端/卖家端/运营端/系统管理端各自独立部署、独立扩缩容、独立发布 |
| 事件总线扩展 | `IEventBus` 接口支持发布订阅，未来可替换为更高吞吐传输（Kafka） |
| 分库分表预留 | 按上下文分库为后续分片预留；GUID 主键便于分布式扩展 |
| 无状态服务 | JWT 无状态认证，应用实例无状态，可水平扩缩容 |

### 6.5 可观测性保障

| 可观测性需求 | 技术保障 |
|--------------|----------|
| 结构化日志 | Serilog 输出 JSON，含 TraceId/SpanId 串联，导出至 ELK/Loki 检索 |
| 链路追踪 | OpenTelemetry 自动埋点 HTTP/EF Core/Redis/MQ，跨服务串联 Trace，对接 Jaeger/Tempo |
| 指标监控 | Prometheus 拉取 `/metrics`，Grafana 可视化，自定义业务指标（订单 TPS、支付成功率、库存预占失败率、通知送达率） |
| 告警 | Alertmanager 基于指标阈值告警（如支付成功率下降、死信堆积、健康检查失败） |
| 健康聚合 | BC11 聚合各模块 `/health` 状态，统一监控面板 |

**统一响应与 API 规范**（支撑可观测性与一致性）：

```json
// 统一响应结构
{
  "code": 200,
  "message": "success",
  "data": { /* 业务数据 */ }
}

// 分页响应
{
  "code": 200,
  "message": "success",
  "data": {
    "items": [ /* ... */ ],
    "total": 1280,
    "page": 1,
    "pageSize": 20
  }
}
```

API 规范要点：RESTful 风格、资源名词复数；`Authorization: Bearer {token}` 鉴权；`Idempotency-Key` 幂等键；时间字段 ISO 8601 UTC；分页 page 从 1 开始、pageSize 默认 20 最大 100。

## 7. 技术风险与缓解措施

本章识别关键技术风险并给出缓解措施，确保架构稳健演进。

| 编号 | 风险 | 影响 | 缓解措施 |
|------|------|------|----------|
| R1 | CQRS 读库同步延迟（秒级），下单瞬间读库库存可能滞后 | 用户看到可购买但实际已售罄 | 读侧库存以 Redis 实时为准；下单走命令侧 Redis Lua 强校验；读库仅用于展示，不作为扣减依据 |
| R2 | Redis 故障导致库存预占、限流、会话失效 | 秒杀/登录/限流不可用 | Redis 主从 + Sentinel 高可用；故障降级策略（回退 DB 悲观锁或临时关闭秒杀）；会话降级至数据库 |
| R3 | 发件箱轮询进程单点或积压 | 事件发布延迟，跨上下文协作滞后 | 轮询进程多实例 + 数据库行锁/乐观锁分片领取；监控 Outbox 积压量告警；积压时横向扩消费实例 |
| R4 | RabbitMQ 单机吞吐瓶颈 | 高并发事件发布/消费阻塞 | 生产环境 RabbitMQ 集群；超大规模日志型事件引入 Kafka 补充；监控队列深度告警 |
| R5 | 支付/通知外部服务商故障 | 支付失败、通知不达 | 渠道主备切换（短信阿里云/腾讯云）；支付失败重试 + 死信人工介入；对账任务校正状态差异 |
| R6 | DDD/CQRS 学习曲线陡，团队落地偏差 | 分层混乱、贫血模型、跨上下文耦合 | 提供分层脚手架模板与编码规范；架构评审把关；共享内核与基础类库降低重复；结对编程与培训 |
| R7 | 多角色端项目配置/代码重复 | 维护成本高、不一致 | 共享内核 + 基础设施公共类库；配置模板化；CI 统一构建 |
| R8 | 共享内核破坏性变更影响多上下文 | 跨上下文回归风险 | 共享内核"只增不改、破坏性变更需协商"原则；版本化集成事件契约；变更走架构评审 |
| R9 | ES 索引与写库数据不一致 | 搜索结果偏差 | 定期全量索引重建（BC11 触发）；对账任务校正；索引重建进度可追踪 |
| R10 | 库存 Redis 与 DB 双写不一致 | 超卖或少卖 | 对账任务周期校正 Redis 与 DB 库存基线；预占失败回滚；监控预占失败率告警 |
| R11 | 跨上下文事件消费幂等失效 | 重复扣库存/重复发积分 | 消费者强制事件 Id + 业务唯一键去重；幂等测试覆盖；死信重投前人工确认 |
| R12 | 延迟消息（订单超时）在大促期间堆积 | 超时取消延迟，库存释放不及时 | RabbitMQ 延迟队列分区；大促前压测延迟队列容量；监控延迟消息积压 |

**风险治理机制**：建立技术风险登记册，定期评审风险状态；每项风险指定负责人与缓解验收标准；关键风险纳入监控告警与混沌演练。

## 8. 技术演进路线

平台采用渐进式演进策略，按业务规模与团队成熟度分阶段推进技术升级，避免过度设计与频繁重构。

### 阶段一：模块化单体奠基（当前，0-6 个月）

**目标**：完成核心功能上线，建立 DDD/CQRS/事件驱动架构基底。

- 11 个限界上下文以模块化单体部署，共享进程但严格上下文边界。
- 写库按上下文分 Schema/库，读库 ES + Redis 就位。
- RabbitMQ + MassTransit 事件总线 + 发件箱模式落地。
- JWT/OAuth2 认证、Redis 限流、支付/通知/存储抽象到位。
- Docker + docker-compose 编排，Serilog/OpenTelemetry/Prometheus 可观测性就绪。

**演进重点**：夯实地基，纪律性保持上下文边界，为后续拆分预留条件。

### 阶段二：核心域拆分与容量优化（6-12 个月）

**目标**：针对高流量核心域独立扩缩容，缓解单进程瓶颈。

- 订单与交易域（BC4）、促销域（BC5）率先拆为独立微服务，独立部署与扩缩容。
- 秒杀/订单高峰流量独立承载，避免影响其他域。
- RabbitMQ 升级集群，ES 扩展分片与副本。
- 引入配置中心（Consul/Apollo）实现支付/通知参数热更新。

**演进重点**：沿限界上下文边界拆分，事件总线由进程内替换为 MQ 跨进程，验证拆分可行性。

### 阶段三：全面微服务化与 K8s（12-24 个月）

**目标**：全上下文微服务化，容器编排自动化。

- 11 个上下文均拆为独立微服务，各自独立库与部署。
- 迁移至 Kubernetes，获得自动扩缩容、滚动发布、自愈能力。
- 引入服务网格（Istio/Linkerd）治理流量、熔断、限流、可观测性。
- 高吞吐事件场景引入 Kafka 补充 RabbitMQ（如行为日志、实时统计）。

**演进重点**：运维自动化，分布式治理成熟，可观测性全景化。

### 阶段四：云原生与智能化（24 个月+）

**目标**：云原生深度优化与智能化运营。

- 多云/混合云部署，按成本与合规选择云厂商。
- 数据中台化，ES/Redis/DB 按域独立云托管（RDS/Elastic Cloud/Managed Redis）。
- 引入 AIOps 智能告警与容量预测；秒杀等峰值场景基于 Serverless 弹性扩容。
- 推荐搜索引入向量检索与机器学习排序。

**演进重点**：成本优化、弹性极致、智能化运营。

### 演进原则

1. **业务驱动**：技术演进以业务流量与团队规模为驱动，避免技术先行。
2. **边界优先**：始终保持限界上下文边界清晰，使任何阶段的拆分成本可控。
3. **可回滚**：每次演进保持可回滚，灰度发布，监控先行。
4. **监控前置**：可观测性在演进前到位，确保演进过程可度量。
5. **契约稳定**：集成事件契约版本化演进，向后兼容，避免破坏性变更阻塞演进。
