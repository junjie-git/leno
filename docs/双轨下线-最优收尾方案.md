# 双轨下线 · 最优收尾方案（无约束版）

> 日期：2026-09-23 · 性质：**设计文档，未实施**
> 前置：`docs/双轨下线-实施方案.md` §7（权威状态）、`docs/库存目标架构-无约束最优方案.md` §8（库存收尾）
> 适用前提（用户已授权，等同库存方案的授权口径）：**数据按全新处理 + 维护窗口可停机（DEC-3 已定 (c) 同类操作）**
> 本文档回答：如果剩余 19 项收尾不受兼容性、历史包袱、迁移成本约束，终点应该长什么样、怎么走。

---

## 0. 五条原则（与库存方案同源）

1. **开关必须删除，而不是打开** —— 一个特性开关是一次未完成的决策。收尾不是 `flag=true`，而是删 flag 与输掉的那条轨。
2. **输掉的轨道连同代码一起删** —— 不保留"回退路径"：回退路径的存在会让两条轨永久共存，这正是双轨的病根。
3. **验证用确定性差分，不用生产灰度** —— 新旧等价性用可重复、可机器判定的 harness 证明，而不是"观察几个星期"。
4. **一个数据只有一个权威，一个机制只有一种实现** —— 写权威、延迟机制、鉴权模型、内部调用前缀，各自收敛为唯一形态。
5. **部署清单只维护一份** —— 端口/镜像/路由等跨清单数据由单一来源生成或校验，消灭"漂移类"问题。

## 1. 终态总览（收尾完成后）

```
服务数：19 → 16（删除 UserAuth / PointsMembership / ReviewAfterSales 三个组合 BC）
特性开关：6 → 0          （Order:UseSagaStateMachine / UsePaymentProcessManager /
                          Promotion:UseRuleEngine / Cart:UseSkuSnapshot / Auth:Mode / AntiCorruption:UseGrpc）
shadow 转发路径：2 → 0    （Saga / Process Manager 的并行影子转发）
内部路由前缀：2 → 1      （仅 internal/v1/*；旧 internal/* 与探测器一并删除）
延迟消息机制：2 → 1      （仅 Quartz 持久化调度器；IBus 直发路径删除）
鉴权模型：2 → 1          （每服务 JwtBearer 直连 RS256/JWKS；GatewayHeader 透传删除）
读模型权威：含糊 → 1     （SQL 为写权威；ES 仅由事件派生，可整库重建，禁止同步双写）
部署清单来源：3 → 1      （端口/服务清单单一来源 + CI 校验）
标识契约：int64+string → string（gRPC 契约单形态）
```

**三条主链的终态**：

```
身份主链   Identity(签发 RS256, 暴露 JWKS) ◀── 各服务 JwtBearer 直连校验（无透传、无共享密钥）
读模型主链 写事务 ──Outbox──▶ 集成事件 ──▶ ES 索引器（唯一写 ES 者）──▶ 购物端查询
           管理端查询直读 SQL（与事件同源，天然一致）
订单主链   创建=同步事务（校验→gRPC 预占→落库→Outbox）；此后=唯一 Saga（到支付）
           支付后=唯一 Process Manager（确认库存/积分/订单状态，独立重试与 DLQ）
```

## 6. 与现行方案的差异（为什么这样更彻底）

| 维度 | 现行方案 | 本方案 |
|------|---------|-------|
| 开关 | 逐个开启并观察 | **删除开关与输掉的分支**（flag 不是状态，是未完成的决策） |
| 回退 | 保留旧实现与回退路径 | **删除**（回退路径是双轨复发的根源；数据按全新处理已消除回退的技术必要） |
| 验证 | 生产观察期 / 灰度 | **确定性差分 harness**（可重复、可机器判定） |
| 退役 | "只读保留一个观察期" | **原子删除**（UserAuth / PointsMembership / ReviewAfterSales 一次性清掉） |
| 一致性 | 人工维护多份清单 | **单一来源 + CI 校验**（消灭漂移类问题） |
| 收尾范围 | 15 项下线 | 15 项 + 库存 4 项验收遗留 + 守护规则（防回潮） |

**预计删除资产**：3 个 BC 工程及其全部部署物料、6 个特性开关、2 条 shadow 转发路径、5 处旧路由、1 个探测器中间件（+40 单测）、1 套旧折扣算法、1 套旧快照读分支、1 条 IBus 直发路径、1 套 GatewayHeader 鉴权分支、1 套 HS256 校验路径。

## 7. 风险前提（诚实说明）

1. 三个组合 BC 的原子退役依赖"数据按全新处理"前提 —— 若个别表有真实数据，需在窗口内先导出再删。
2. 差分 harness 的语料质量决定 D3 的信心；语料不足时不得放行删除。
3. 阶段 3 合并窗口的动作较多（鉴权切 RS256 影响所有服务 + 三个 BC 退役）—— 建议窗口前在 staging 完整演练一次。

### 终态决策：删字段 + reserved（并修订 ADR-0005）

原 `buf.yaml` 启用 `FIELD_NO_DELETE`（一律禁止删除字段），与 ADR-0007 预告的"迁移完成后可删除
int64 字段"直接冲突。实测确定精确替代方案（已在 CI 中生效，双向验证）：

| 配置 | 删已 reserved 字段 | 删未 reserved 字段 |
|------|------------------|------------------|
| `use: [FILE]` + `except: [FIELD_NO_DELETE]` | 放行 | **也放行（守护失效，反例被抓到）** |
| `use: [FILE, FIELD_NO_DELETE_UNLESS_NUMBER_RESERVED, FIELD_NO_DELETE_UNLESS_NAME_RESERVED]` + `except: [EXTENSION_NO_DELETE, FIELD_NO_DELETE]` | 放行 ✅ | **拦截 ✅**（报 `deleted without reserving the number/name`） |

要点：`FIELD_NO_DELETE_UNLESS_*` **不在 `FILE` 类别内**，必须显式列出；`except: FIELD_NO_DELETE`
只关掉"无条件禁止"那条。ADR-0005 据此修订为"**允许删除，但必须 reserved 编号与名**"。

## 附：秒杀结算执行记录（2026-09-24）—— 台账写入落点修正 + 单向校验

### 侦察结论：秒杀链路此前完全没有台账

- Promotion 的秒杀下单（`SeckillAppService.PlaceOrderAsync`）只做 Redis 原子预扣 + 限购校验，
  然后写自己的 `SeckillPreOccupationRecord` 并发 `SeckillOrderCreatedEvent`；
- **Order 的秒杀建单（`SeckillOrderCreationService`）压根不碰库存** —— 只查 SKU、建 `OrderType.Seckill` 订单、发确认回执；
- 结果：`stock_reservations`（DEC-4 后的库存权威）里**没有任何秒杀预占**，Inventory 的可用量高估
  "秒杀已售"部分 → 同一 SKU 若也在普通渠道售卖，存在**超卖**风险。

### 落点修正（与方案字面口径的差异，需登记）

方案原文是"秒杀创建流程改为**配额扣减成功后即调** `ReserveAsync`"，字面指向 Promotion 热路径。实测权衡后改放
**Order 的秒杀建单**，理由：

1. **零新增跨 BC 依赖**：Order 已有 `IInventoryGateway`（gRPC 同步预占 + 三个异步命令），Promotion
   此前**完全没有**库存客户端，也**没有任何库存配置**（无 ServiceUrls/内部键）——放进 Promotion 要新建一条
   跨 BC 同步链路；
2. **热路径不变**：Promotion 的热路径按设计只碰 Redis（避免 DB 参与扣减）；写入放在异步的建单流程，不牺牲秒杀吞吐；
3. **一个机制只有一种实现**：所有订单（普通/秒杀）的预占都由 Order 发起，确认/释放走既有 Order 生命周期
   （`StockConfirmConsumer` / `OrderTimeoutDelayMessageConsumer` / `RefundCompletedEventConsumer`），不新增第二条口径。

**不等式方向随之修正**：台账写入晚于准入（事件排空窗口），故单向校验为
「**台账量 ≤ 已扣减配额**」（`已扣减配额 = total_stock − Redis 剩余`）——即"落地不得超出准入"，
而非方案字面的"配额 ≤ 台账"。

### 改动

| 位置 | 内容 |
|---|---|
| `SeckillOrderCreationService` | 建单前调 `ReserveBatchAsync(orderId, {skuId: qty})`：预占失败 → 不建单 + 发失败回执（Promotion 据此回退 Redis 配额与 DB 基线）；预占成功但落库失败 → **先释放台账预占**再发失败回执（避免"无主预占"永久占用库存） |
| `SeckillOrderCreationService` | **补调度支付超时**（`queue:order-timeout`，Quartz 持久化调度器）—— 此前秒杀订单从不调度超时，订单到期无人取消；加了台账预占后若不补，未支付订单的预占将永久泄漏 |
| 单测 | `SeckillOrderCreationServiceTests` 50 → **52**：新增"预占不足不发单/发失败回执"、"落库失败先释放预占再发回执"；成功用例夹具改断言"先预占→再建单→再调度超时" |
| 集成测试 | `SeckillOrderFlowIntegrationTests` 补 `IInventoryGateway` / `IMessageScheduler` mock |
| 校验工具 | 新增 `scripts/verify/SeckillLedgerReconcile`（C# 控制台）+ `scripts/verify/seckill-ledger-reconcile.sh` 包装：不变量 1 台账覆盖（Promotion 未回退记录 ↔ 台账逐单一致、状态非 Released/Returned）、不变量 2 配额上限（需 `--redis`）；退出码 0/1/2 |
| 顺手修复 | `InventoryE2E`（阶段 5 产物）查了不存在的列 `SUM(reserved_qty) FROM stock_reservations` → 改为 `SUM(quantity)`（该断言原本一跑就报"列名无效"） |

### 保留（按你的决策）

Promotion 的 `SeckillPreOccupationRecord` + 两个事件消费者 + `SeckillPreOccupationCompensationService`
**保留**：它不承载库存数，而是"配额已扣但订单未落地"的补偿依据（5 分钟阈值扫描未履约记录并回退 Redis + DB 基线），
与台账互补而非重复。**注意**：其"履约"标记由 Order 建单回执触发，因此不会误回收仍存活但未支付的订单配额。
