# 双轨下线 · 最优收尾方案（无约束版）

> 日期：2026-09-23 · 性质：**设计文档，未实施**
> 前置：`docs/双轨下线-实施方案.md` §7（权威状态）、`docs/库存目标架构-无约束最优方案.md` §8（库存收尾）
> 适用前提（用户已授权，等同库存方案的授权口径）：**数据按全新处理 + 维护窗口可停机（DEC-3 已定 (c) 同类操作）**
> 本文档回答：如果剩余 19 项收尾不受兼容性、历史包袱、迁移成本约束，终点应该长什么样、怎么走。

---

## 0. 五条原则（与库存方案同源）

1. **开关必须删除，而不是打开** —— 一个特性开关是一次未完成的决策。收尾不是 `flag=true`，而是删 flag 与输掉的那条轨。
2. **输掉的轨道连同代码一起删** —— 不保留"回退路径"：回退路径的存在会让两条轨永久共存，这正是双轨的病根。
3. **验证用确定性差分，不用生产灰度** —— 新旧等价性用可重复、可机器判定的 harness 证明，而不是"观察几个星期"。
4. **一个数据只有一个权威，一个机制只有一种实现** —— 写权威、延迟机制、鉴权模型、内部调用前缀，各自收敛为唯一形态。
5. **部署清单只维护一份** —— 端口/镜像/路由等跨清单数据由单一来源生成或校验，消灭"漂移类"问题。

## 1. 终态总览（收尾完成后）

```
服务数：19 → 16（删除 UserAuth / PointsMembership / ReviewAfterSales 三个组合 BC）
特性开关：6 → 0          （Order:UseSagaStateMachine / UsePaymentProcessManager /
                          Promotion:UseRuleEngine / Cart:UseSkuSnapshot / Auth:Mode / AntiCorruption:UseGrpc）
shadow 转发路径：2 → 0    （Saga / Process Manager 的并行影子转发）
内部路由前缀：2 → 1      （仅 internal/v1/*；旧 internal/* 与探测器一并删除）
延迟消息机制：2 → 1      （仅 Quartz 持久化调度器；IBus 直发路径删除）
鉴权模型：2 → 1          （每服务 JwtBearer 直连 RS256/JWKS；GatewayHeader 透传删除）
读模型权威：含糊 → 1     （SQL 为写权威；ES 仅由事件派生，可整库重建，禁止同步双写）
部署清单来源：3 → 1      （端口/服务清单单一来源 + CI 校验）
标识契约：int64+string → string（gRPC 契约单形态）
```

**三条主链的终态**：

```
身份主链   Identity(签发 RS256, 暴露 JWKS) ◀── 各服务 JwtBearer 直连校验（无透传、无共享密钥）
读模型主链 写事务 ──Outbox──▶ 集成事件 ──▶ ES 索引器（唯一写 ES 者）──▶ 购物端查询
           管理端查询直读 SQL（与事件同源，天然一致）
订单主链   创建=同步事务（校验→gRPC 预占→落库→Outbox）；此后=唯一 Saga（到支付）
           支付后=唯一 Process Manager（确认库存/积分/订单状态，独立重试与 DLQ）
```

| 项 | 终态决策 | 改动清单 |

## 4. 验证策略：确定性 harness 全面取代"观察期/灰度"

| 场景 | harness | 判定 |
|------|---------|------|
| 折扣引擎等价（D3） | 属性化差分测试（语料生成 + 双引擎逐字段比对） | CI job，零不等价或不等价已裁决固化 |
| 快照格式（D4） | 迁移后全表断言 + 读路径单测 | CI job |
| Saga / PM（D1/D2） | staging 回放脚本（六链路订单 + 支付后三子任务 + 注入失败补偿） | 脚本退出码 0 + DB 终态断言 |
| 旧路由（C2） | 内部调用方 E2E（改后路径） | 编译 + E2E |
| 身份切换（A6） | 窗口演练脚本：登录/注册/角色/地址/OAuth Client 五链路 | 窗口内 checklist 全绿 |

**原则**：任何"需要观察"的判定，先问能不能改成"可断言的差分"；不能改的（如生产流量形态）才用观察，并且观察也要有明确时长与零命中判据。

## 6. 与现行方案的差异（为什么这样更彻底）

| 维度 | 现行方案 | 本方案 |
|------|---------|-------|
| 开关 | 逐个开启并观察 | **删除开关与输掉的分支**（flag 不是状态，是未完成的决策） |
| 回退 | 保留旧实现与回退路径 | **删除**（回退路径是双轨复发的根源；数据按全新处理已消除回退的技术必要） |
| 验证 | 生产观察期 / 灰度 | **确定性差分 harness**（可重复、可机器判定） |
| 退役 | "只读保留一个观察期" | **原子删除**（UserAuth / PointsMembership / ReviewAfterSales 一次性清掉） |
| 一致性 | 人工维护多份清单 | **单一来源 + CI 校验**（消灭漂移类问题） |
| 收尾范围 | 15 项下线 | 15 项 + 库存 4 项验收遗留 + 守护规则（防回潮） |

**预计删除资产**：3 个 BC 工程及其全部部署物料、6 个特性开关、2 条 shadow 转发路径、5 处旧路由、1 个探测器中间件（+40 单测）、1 套旧折扣算法、1 套旧快照读分支、1 条 IBus 直发路径、1 套 GatewayHeader 鉴权分支、1 套 HS256 校验路径。

## 7. 风险前提（诚实说明）

1. 三个组合 BC 的原子退役依赖"数据按全新处理"前提 —— 若个别表有真实数据，需在窗口内先导出再删。
2. 差分 harness 的语料质量决定 D3 的信心；语料不足时不得放行删除。
3. 阶段 3 合并窗口的动作较多（鉴权切 RS256 影响所有服务 + 三个 BC 退役）—— 建议窗口前在 staging 完整演练一次。

  `jwks_uri` 按请求主机推导）—— 供各服务 JwtBearer 的 `MetadataAddress` 自动拉取并缓存公钥。

  （签名公钥自动拉取缓存）；删除 `Auth:Mode` 与 GatewayHeader 方案注册（D-4 零信任：不信任上游注入头）

  （`ValidateTokenAsync` / `BuildValidationParameters`），保留 Claim 读取助手
  （`GetUserId/GetRole/GetShopId/GetSessionId`，`CurrentUserContext` 在用）与刷新令牌生成
- 网关 `Program.cs`：验签改 JWKS（保留"延迟解析"以兼容测试的配置覆盖）
- **14 个 appsettings 统一**：删 `Auth` 节；`Jwt` 节删 `SecretKey`/`Enabled`，
