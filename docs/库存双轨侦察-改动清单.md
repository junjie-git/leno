## 1. 现状全景：两条并行库存流写同一批数据

### 1.1 Flow B —— 权威路径（Inventory BC，已建成）


  proto 头注明确写着"GrpcService 实现待后续任务接入（遗留项）"）

## 3. 目标架构（Inventory 为准）

```
Order BC                                Inventory BC（库存唯一权威）
────────                                ──────────────────────────
OrderAppService（下单，需同步 bool）──gRPC ReserveStock──▶ InventoryInternalService（待实现）
Saga / 超时 / 退款 / 强取 / StockConfirm ──MassTransit 命令──▶ Reserve/Confirm/ReleaseStockCommand 消费者
StockAdjustedEvent ──只由 Inventory 消费──▶ SetBaseLine（单一写入方）
补偿重试 / 对账 / 库存聚合 / Redis 权威数据 ──全部归 Inventory──▶
Order 保留：Saga 状态、ReservationIds（供按单查询）、补偿"发起权"（发命令），不再持有库存写路径
```

**核心思路：`IInventoryRepository` 端口不动，换适配器** —— Order 的 6 个调用方零改动，
底层从"直写 Redis"换成"gRPC 调 Inventory"。这把改动面从"全链路重构"压缩到"适配器替换 + 删码"。

## 5. 需要决策的点

### D-1 同步预留走 gRPC 还是 HTTP（推荐 gRPC）
- **gRPC（推荐）**：proto 已定义（含 `ReserveStockResponse.success/failure_reason/reservation_id`，正好承接
  `ReserveAsync` 的 bool 语义与 reservation_id 回填），库存是下单强同步依赖，gRPC 语义与性能都合适；
  且 Order 侧 **端口不变、只换适配器**，改动面最小。
- HTTP：需要在 Inventory 补 4 个内部写端点（现在只有查询），并新写 DTO/响应包装 —— 纯增量工作，无额外收益。

### D-2 补偿与对账归属（推荐全归 Inventory）
- **归 Inventory（推荐）**：数据所有方负责补偿与对账；Order 只保留"发起权"（发命令）。
  Order 的补偿表/后台服务/对账服务下线（删码约等于批次 3 的体量）。
- 保留双份：不推荐 —— 与 DEC-4"以 Inventory 为准"矛盾，双份补偿还会重复重试同一失败操作
  （两套补偿表各自重试，幂等键不一致时可能双重释放）。

### D-3 Order 的 `StockReservation` 聚合去留（推荐保留为"订单视角快照"）
- Saga 补偿需要"按 ReservationId 释放"的本地记录；建议 Order 保留聚合作**只读快照/审计**，
  写入方改为 Inventory 回执事件（`StockReservedIntegrationEvent` 已带 ReservationItems）。
  若倾向彻底删净，则 Order 补偿逻辑完全依赖 Inventory 的命令幂等 —— 也可行，但删得更深。
